# Запуск пилота inrou

Подготовлены подключение Директа по OAuth, выбор счётчика/целей Метрики, очередь синхронизации и запуск существующего детерминированного аудита. Объявления, ставки и бюджеты сервис не меняет. Внешняя LLM не добавлена.

## Локально

Нужен работающий Docker Engine. Из корня проекта:

```powershell
python deploy/configure_local.py
docker compose --env-file deploy/.env up --build -d
```

Адрес: http://localhost:10000. Проверка: http://localhost:10000/api/health.
PostgreSQL недоступен извне. Генератор один раз создаёт `deploy/.env`; повторный запуск не перезаписывает ключи. Не коммитить и не пересоздавать этот файл, если БД уже содержит токены.

На первом старте bootstrap создаёт отдельные роли БД и запускает существующие миграции. API работает как `app_rw`, очередь — `app_system`, чтение токенов — `app_token`. Существующая БД не сбрасывается. Для сервера с заранее созданными ролями вместо bootstrap задаются `API_DATABASE_URL`, `WORKER_DATABASE_URL`, `WORKER_QUEUE_DATABASE_URL`; миграции выполняются отдельно с `MIGRATION_DATABASE_URL`.

## Временный бесплатный стенд Render

В корне есть `render.yaml`: один web service и PostgreSQL с `plan: free`. Сервис объединяет frontend, API и опциональный worker, чтобы не требовать платного background worker. Нужны ваш аккаунт Render и доступ Render к вашему репозиторию. Создайте Blueprint из нужной ветки после переноса и сохранения изменений в Git.

Регистрация, почта, OAuth и worker по умолчанию выключены. Это не обход юридических проверок. Создание Blueprint само по себе не означает, что пользователи могут подключать реальные кабинеты.

Ограничения Render: остановка web service после 15 минут без запросов, бесплатная БД на 30 дней, SMTP-порты 25/465/587 закрыты, квоты CPU/RAM/часов/трафика. Worker тоже останавливается вместе с web service; очередь хранится в БД и продолжается при пробуждении. Нельзя обещать круглосуточный фоновый анализ. Не добавляйте платные ресурсы или платёжный метод ради этого шаблона.

Источники: https://render.com/docs/free и https://render.com/docs/blueprint-spec.

Регион шаблона — Frankfurt. В проекте предусмотрено хранение клиентских данных в РФ. До отдельного решения о месте обработки используйте этот стенд только для демонстрации, без клиентских ПД, рекламных данных и токенов. Для реального пилота предпочтителен подготовленный Docker-образ на согласованном сервере в РФ.

Docker-образ и шаблон Render требуют проверки сборкой на Docker Engine и на аккаунте Render. Успешные локальные Python/Next.js проверки этого не заменяют. Для bootstrap нужны права создавать роли PostgreSQL; если провайдер их не даёт, роли создаёт оператор, без ослабления RLS.

## Что включить для реальных клиентов

1. Подготовить HTTPS-адрес и проверить `/api/health`.
2. Для входа по email настроить почту, а для Директа/Метрики — **одно** API-приложение (`YANDEX_API_*`) с правами `direct:api`, `metrika:read` и одобренным доступом к API Директа. Яндекс ID (`YANDEX_LOGIN_*`) — только дополнительный прежний способ входа, для выбранного email-сценария отдельное приложение не требуется. Актуальная инструкция Яндекса также описывает `passport:business` для авторизации от организации; выданные права проверяются отдельно.
3. Callback входа: `https://<домен>/api/auth/yandex/callback`. Для нового приложения «Для доступа к API» Яндекс фиксирует `YANDEX_API_REDIRECT_URI=https://oauth.yandex.ru/verification_code`: клиент начинает подключение в своём личном кабинете, открывает Яндекс в новой вкладке и вставляет полученный код в INROU. Код привязан PKCE к зашифрованной попытке подключения, пользователю и пространству; срок попытки — 10 минут. Клиент не передаёт пароли, Client secret или OAuth-токены оператору. Если у существующего приложения настроен web callback, сохраните `https://<домен>/api/direct/callback` — автоматический возврат тоже поддерживается. `API_ALLOWED_ORIGINS` и `INROU_APP_ORIGIN` — точный HTTPS origin INROU без пути; адрес Яндекса в allowed origins не добавлять.
4. Внести согласованные реальные юридические тексты и реквизиты в реестр `backend/app/legal/texts/`. Зарегистрировать версии в `documents.py`. Для утверждённых документов задать точные SHA256 в `API_SIGNUP_APPROVED_HASHES`. **Нельзя утверждать хэши шаблонов.** Ключи `privacy`, `cookies`, `requisites` теперь поддерживаются и в API, и на сайте.
5. Для выбранного входа по email можно использовать Unisender Go: `INROU_EMAIL_ENABLED=1`, `INROU_EMAIL_ORIGIN`, приватный `INROU_AUTH_HMAC_KEY`, `INROU_MAIL_PROVIDER=unisender`, `INROU_MAIL_API_KEY` и подтверждённый `INROU_SMTP_FROM`; API работает через HTTPS. SMTP на бесплатном Render ограничен исходящими портами. Перед включением нужны тест доставки, SPF/DKIM, почтовый worker и проверенный ingress.
6. Создать ключ `TOKEN_ENCRYPTION_KEY_1` (base64 от 32 случайных байтов), надёжно сохранить его и установить `YANDEX_API_ENABLED=1`. Локальный генератор уже создаёт ключ. Секреты вводятся в окружении, не в чат и не в Git.
7. После регистрации добавить разрешённые workspace ID в `PILOT_WORKSPACE_IDS`, указать дату с часовым поясом в `PILOT_ACCESS_UNTIL`. Например, форма даты `2026-11-01T00:00:00+03:00`; срок выбирает владелец. Отсутствующий/истёкший/неверный срок не даёт доступ. Это отдельный допуск к пилоту, а не запись об оплате.
8. Запустить `python -m app.worker.runner` из `backend` либо установить `WORKER_ENABLED=1` в объединённом образе. Нужны DSN двух рабочих ролей, те же ключи OAuth/шифрования/пилота, `RELEASE_COMMIT_SHA` (40 hex) и уникальный `RELEASE_BUILD_ID`. На Render SHA берётся из `RENDER_GIT_COMMIT`; build ID всё равно задаётся явно. Проверки должны относиться к этой версии исходников, а не к другой dirty-копии.
9. После регистрации каждый клиент в своём кабинете открывает «Подключения», указывает логин Директа, счётчик, ID целей и при необходимости целевой CPA. Затем разрешает доступ в Яндексе. В режиме `verification_code` клиент возвращается на прежнюю вкладку INROU и вводит код; при ошибке или истечении срока начинает подключение заново. Яндекс проверяет доступ, backend дополнительно сверяет цели счётчика, шифрует токены и ставит загрузку в очередь. В пилоте — один рекламный кабинет на пространство. OAuth-приложение, его секрет и доступ к API настраивает владелец INROU один раз; клиентам не требуется создавать собственные приложения или передавать секреты в чат. Само наличие формы подключения не включает регистрацию: до открытия пилота нужны настроенный вход, утверждённые документы и срок допуска из пунктов выше.
10. Дождаться завершения загрузки и аудита, обновить страницу и сверить данные с Директом на реальном кабинете. Новые live-снимки требуют подтверждённой RUB-валюты каждой кампании; другая или неизвестная валюта останавливает sync до записи. Исторические снимки автоматически не перепроверяются. Без счётчика/целей конверсионные выводы будут недоступны. Успешная загрузка не означает, что найдены проблемы или доказана экономия.

До сборки задать `NEXT_PUBLIC_SITE_URL` равным публичному HTTPS `INROU_APP_ORIGIN`. Compose передаёт его и `INROU_STAGING` через `build.args` при использовании `--env-file deploy/.env`; `env_file` сервиса применяется только к runtime. Для закрытого пилота оставить `INROU_STAGING=1`, `INROU_DEMO=0`. После смены публичного адреса пересобрать frontend и проверить canonical/sitemap готовой сборки. Локальный генератор задаёт адрес localhost и staging; он не настраивает публичный домен автоматически.

Владельцу без внешних сервисов: [пошаговый план запуска и приёмки](../docs/LAUNCH_READINESS.md). Заявка Яндекса рассматривается до 7 дней; запуск с реальными данными в день создания приложения не гарантируется.

Документация Яндекса: https://yandex.ru/dev/direct/doc/ru/concepts/register и https://yandex.ru/dev/direct/doc/ru/token.

## IP посетителя и ограничения входа

За собственным Caddy используйте `deploy/Caddyfile`, оставив порт Next.js закрытым от внешних запросов. Caddy всегда заменяет `X-Real-IP`. Только тогда установите `INROU_CLIENT_IP_HEADER=x-real-ip` и одинаковый случайный `API_PROXY_HMAC_KEY` длиной минимум 32 символа на frontend/API. Next.js подписывает IP, метод, путь и время; backend игнорирует неподписанные/просроченные/подменённые данные.

На Render не включайте доверие к произвольному IP-заголовку. Email-вход в шаблоне выключен. Перед его включением за другим ingress нужно проверить, какой заголовок он гарантированно перезаписывает. Простое копирование `X-Forwarded-For` небезопасно.

## Сохранность

Для открытого теста новых клиентов используйте `PILOT_OPEN_ACCESS=1` вместе с датой окончания `PILOT_ACCESS_UNTIL` в ISO 8601 с часовым поясом. После этой даты бесплатный допуск прекращается. Проверки входа, роли и рабочего пространства сохраняются; оплаченная подписка не создаётся.

Перед миграциями сделайте `pg_dump` и проверьте восстановление на отдельной БД. Для локального контейнера можно выполнить `pg_dump` в контейнере с `-f /tmp/inrou.dump`, затем скопировать файл через `docker compose cp db:/tmp/inrou.dump <закрытый-путь>`. Не выгружайте дамп в публичные artifacts или репозиторий.

Храните резервную копию БД и ключей шифрования раздельно и ограничьте доступ. Проверка восстановления в рамках этой задачи не выполнена. Render free не заменяет план резервирования, а создание платёжной записи не заменяет выдачу доступа к пилоту.


## Проверка подготовки к запуску

Из корня: `python deploy/readiness.py`. Команда читает конфигурацию без внешних запросов и печатает только статусы проверок. Код 2 означает неполную конфигурацию; код 0 подтверждает только её полноту, не реальную доставку, права в Директе, изоляцию клиентов или готовность к релизу. Утверждение хэша шаблона документа не проходит проверку.

До включения email проверить ingress: два синтетических клиента должны получать разные peer-ограничения; подстановка клиентом `X-Real-IP`, `X-Forwarded-For`, `X-Inrou-Client` и подписи не должна менять доверенный адрес. Порт Next/API должен быть недоступен в обход ingress. Секрет подписи одинаков на frontend/API, длиной минимум 32 символа. Само наличие `INROU_CLIENT_IP_HEADER` не доказывает перезапись заголовка.

Затем пройти signup → письмо → подтверждение → login → reset для синтетических адресов, проверить чужой workspace и отозванную сессию; подключить read-only Директ и выполнить первый/повторный sync. Зафиксировать версию сборки, время, обезличенные результаты и отрицательные сценарии. Реальные тексты, реквизиты, подтверждённый домен отправителя и аккаунт ЮKassa настраивает владелец вне Git.

## Очистка данных

`RETENTION_ENABLED=1` включает отдельный процесс `app.worker.retention_runner` с `RETENTION_DATABASE_URL` роли `app_deleter`. Bootstrap выдаёт этот DSN отдельно; API и основной worker его не получают. Очистка выполняется сразу и затем раз в 24 часа, неполные пачки/ошибки повторяются через 60 секунд. В preview этот процесс включён отдельно от загрузки рекламных данных.

После восстановления выполнить из `backend`: `python -m app.worker.retention_runner --once`; требуется код выхода 0 до открытия доступа. См. `docs/DISASTER_RECOVERY.md`. Образ устанавливает фиксированный runtime из `backend/requirements.lock.txt`; обновлять lock отдельной проверенной правкой вместе с `requirements.txt`.


## Платежи: ЮKassa

Подключён разовый заказ на одно пространство: Контроль → `start` (2990 ₽, 1 аккаунт), Бизнес → `business` (4990 ₽, 5), Агентство → `business_plus` (9990 ₽, 15). Новый период — 30 дней плюс существующие 3 дня на продление, без автосписаний. Прежние цены подписок сохраняются. До окончания оплаченного доступа смена тарифа и досрочная покупка недоступны.

Конфигурация и порядок тестирования: `backend/app/billing/README.md`. В ЮKassa указывается публичный callback `https://<домен>/api/billing/yookassa/webhook`. Сначала тестовый магазин и одобренные параметры чека. Реальные ключи вводятся в окружении хостинга. Оплата выключена по умолчанию; переключатели допуска не заменяют регистрацию магазина или юридическую проверку.

После возврата статус сверяется сервером через GET ЮKassa. Заказ восстанавливается на странице тарифов даже после закрытия вкладки. При неопределённом результате повторяется тот же заказ; новый платёж не создаётся. Спустя 24 часа неизвестное создание требует ручной сверки. `python -m app.billing.reconcile` проверяет известные платежи без создания списаний; запускать ежедневно отдельным заданием и реагировать на ненулевой код. Сверка выплат с банковским счётом и бухгалтерией выполняется отдельно и пока не автоматизирована.

## Очередь восстановления пароля

Запрос восстановления всегда фиксируется в глобальной закрытой очереди до поиска аккаунта и отвечает 202 после COMMIT. Ответ означает принятие запроса: письмо отправляется только для подходящего аккаунта. Ошибка записи очереди возвращает 503 для любого адреса.

Объединённый `deploy/serve.py` при включённом `INROU_EMAIL_ENABLED` запускает отдельный `app.worker.auth_mail_runner` независимо от Direct worker. Ему нужны `WORKER_QUEUE_DATABASE_URL` роли `app_system`, параметры почтового провайдера и тот же `INROU_AUTH_HMAC_KEY`, который использует API. При раздельном размещении запустите из `backend`: `python -m app.worker.auth_mail_runner`; `--once` выполняет до 25 доступных задач. Preflight проверяет наличие DSN, но не доказывает работу процесса.

Воркер арендует задачу, атомарно готовит reset token и повторяет ту же ссылку при сбое почтового провайдера до 15 минут от запроса. UUID lease защищает от подтверждения чужой повторной аренды. Доставка at-least-once: сбой после принятия письма провайдером может привести к повторному письму с той же ссылкой. Истёкшая задача больше не отправляется, пользователь может запросить новую ссылку. Недоступность дольше срока ссылки требует нового запроса.

Сырой токен в очередь не записывается: он выводится HMAC с разделением доменов из случайного UUID задачи. Не меняйте auth HMAC key при наличии задач: сначала осушите очередь либо дождитесь истечения срока всех задач (поле expires_at). Адрес хранится до завершения/истечения задачи; воркер удаляет просроченные записи, отдельный retention удаляет их также при отключённой почте. Проверьте backlog и повтор после временного сбоя перед коммерческим включением.


Подтверждение регистрации использует ту же закрытую очередь. Создание pending signup и задачи письма фиксируется одной транзакцией; HTTP202 подтверждает принятие запроса и не раскрывает наличие аккаунта при сбое почтового провайдера. Срок задачи подтверждения берётся из точного `email_pending_signups.expires_at` и повтором отправки не продлевается. Токены reset/verify разделены HMAC-доменами. Повторный запрос одного назначения заменяет прежнюю задачу того же адреса; запоздалая аренда не может подготовить новый токен вместо актуального.
