# Спецификация продукта AdPilot — v1.0

> Решение владельца продукта 2026-10-02. Документ для разработки: какие принципы делают AdPilot системой, которой можно
> доверить решения о деньгах, как они проверяются и как выглядят в интерфейсе. Объём версий и список правил задаёт
> [STRATEGY.md](STRATEGY.md) → [VERSION_SCOPE.md](VERSION_SCOPE.md); форматы данных — [API_CONTRACT.md](API_CONTRACT.md).
> Здесь они не пересказываются, только связываются в требования к продукту. При расхождении правы первоисточники.

**Позиционирование:** AdPilot показывает, где рекламный бюджет расходуется неэффективно, объясняет почему и помогает
исправить — с доказательством каждого расчёта. Не «AI управляет вашей рекламой».

## 1. Пять принципов — проверяемые требования

Каждый принцип — требование с проверкой. Функция, которая нарушает принцип, не выпускается, даже если «работает».

### P1. Evidence First — у каждой цифры есть происхождение
- Любое число в API, UI, Telegram и объяснении — объект `Value` (API_CONTRACT §2): `amount` строкой-Decimal, `unit`,
  `calculation_type` (`actual` · `estimated` · `unavailable`), `source`, `period`, `data_status`, `data_sufficiency`,
  `formula`, `rule_version`. Один канонический объект на пути БД → API → AI → UI.
- Фронтенд не вычисляет и не переименовывает смысл цифры: только отображает контракт (§4.1).
- **Проверка:** инварианты `Value` в `app/contract.py` (тесты); TypeScript-тип, где `amount: null` возможен только у
  `unavailable`; тест сериализации API (`app/api/serialize.py`).

### P2. Rules First — деньги считает детерминированный код
- Конвейер: Директ / Метрика → снимок → нормализованные агрегаты → rule engine → finding → safety policy → рекомендация.
  AI получает готовый finding и объясняет его; он не считает суммы, CPA и не решает, есть ли проблема.
- Правило версионируется (`high_cpa_target@1`); изменение порога или формулы → `@2`. Старые findings ссылаются на свою
  версию и задним числом не меняются.
- **Проверка:** тест импортов (`rules/`, `audit/` не импортируют `ai/`); golden-набор по трём правилам (AI_GOVERNANCE.md
  §4) — новая версия правила включается только после прохождения.

### P3. Human Control — решение принимает человек
- Уровни действия: `inspect_only` («Проверьте») < `review` («Проверьте перед изменением») < `change` («Можно
  изменить»). Safety policy только понижает уровень правила, никогда не повышает (ARCHITECTURE §4.1).
- **v1.0: AdPilot не меняет кабинет.** Кнопка действия — «Принять к выполнению», изменение человек вносит в Директе
  сам, AdPilot сверяет и измеряет. «Применить» через API — v1.1 (EXECUTION_SAFETY.md).
- **Проверка:** клиент Директа в v1.0 вызывает только методы чтения из allowlist (тест, ARCHITECTURE §11).

### P4. Closed Loop — каждая рекомендация заканчивается измерением
- Цикл: проблема → почему → что сделать → решение → ручное выполнение → сверка по Директу → замер через 7 дней.
- Исходное состояние объекта фиксируется при «Принять» (API_CONTRACT §6.1); «Сэкономлено ≈» — только по подтверждённым
  выполнениям, метод «до/после без контрольной группы» (ECONOMICS.md).
- **Проверка:** тесты замера (`audit/measurement.py`, `worker/measure.py`); на пилоте — метрика «есть ли хотя бы один
  подтверждённый результат» (STRATEGY §6).

### P5. Everything Is Traceable — любое число можно раскрыть
- Цепочка: число → период → снимок (`snapshot_id`) → версия правила → релиз кода (`release_id`) → finding →
  объяснение → рекомендация → решение человека → сверка → замер. Звенья append-only на уровне БД.
- В UI у каждой суммы есть «Откуда это число?» (§4.3).
- **Проверка:** триггеры append-only и тесты `test_schema*.py`; тест API — у каждой рекомендации есть `snapshot`,
  `rule_version`, `period`.

## 4. UX-паттерны

### 4.1 Отображение `Value` — единственный способ показать число

| `calculation_type` | Вид | Подпись |
|---|---|---|
| `actual` | `23 400 ₽` | «Факт · Яндекс Директ · 1–30 сентября» |
| `estimated` | `≈ 18 000 ₽` | «Оценка · как посчитано» (формула в подсказке) |
| `unavailable` | «Недостаточно данных» | причина и что подключить: «Нет конверсий за период» |

- `0 ₽` показывается только если это факт. Отсутствие данных — никогда не ноль и не прочерк.
- `data_status = partial` → «данные за последние дни могут уточниться».
- Компонент один на весь фронтенд (`<ValueView>`); прямой вывод `amount` в разметку запрещён линтер-правилом или
  ревью.

### 4.2 Свежесть данных — видна всегда
- В шапке кабинета: «Данные актуальны на 02.10.2026, 18:42» (время последнего снимка, пояс МСК).
- Рядом — источники: «Директ ● актуально», «Метрика ● актуально» / «⚠ обновление N мин назад» / «✕ нет доступа —
  переподключить». В v1.0 источников два; CRM — позже.
- Устаревшие данные (порог — ARCHITECTURE §2.6) снижают уверенность рекомендаций и показываются на «Сегодня».

### 4.3 «Почему» — центральный паттерн рекомендации
Порядок блоков фиксирован: **Что → Почему → Что сделать → Решение → Проверка.**

```
CPA выше цели на 67%                                   ← Что (заголовок из finding)
Почему: расход +24%, конверсии −10%;                   ← Почему (факты из evidence, каждый — Value)
        основной вклад — кампания «Поиск / Москва»
Источник: Яндекс Директ · 25.09–01.10 · факт           ← происхождение
Что сделать: снизить целевую цену конверсии на 10%    ← действие (уровень review/change)
[Принять к выполнению] [Не буду] [Позже]               ← решение (v1.0 — ручное)
Проверка: через 7 дней после выполнения               ← обещание замера
```
- Каждый факт в «Почему» раскрывается в «Откуда это число?»: период, кампании, расход, конверсии, правило и версия,
  время расчёта, какие данные были доступны.
- Текст «Почему» пишет AI только из фактов finding (claims → evidence, AI_GOVERNANCE §2); если AI недоступен или ответ
  не прошёл проверку — шаблонный текст. Блок работает без LLM.

### 4.4 История решений — продуктовая фича, а не журнал
Экран «История»: по каждой рекомендации — карточка цикла.
```
25 сентября · AdPilot нашёл: CPA выше цели на 67% (high_cpa_target@1)
Рекомендация: −15% целевой цены конверсии
Вы: приняли к выполнению 25.09 · отметили «выполнено» 26.09
Сверка: изменение подтверждено по данным Директа 27.09
Проверка через 7 дней: CPA −21,4% · Сэкономлено ≈ 9 800 ₽ (расчётный эффект, без контрольной группы)
```
- Строится из append-only событий; ничего не пересчитывается задним числом.
- Фильтры: результат подтверждён / не подтверждён / ждёт замера / отклонено (с причиной).
- Это главный экран ценности для агентства: «я принял 6 рекомендаций и знаю их эффект». Экспорт для клиента
  агентства — после v1.0.

### 4.5 Ctrl+K — вход в продукт
Команды v1.0 — только навигация и готовые выборки, без генерации текста:
- «Найти кампанию…», «Рекомендации, требующие решения», «Расход с признаками неэффективности за 7 дней»,
  «Кампании без конверсий», «Площадки РСЯ без конверсий», «История решений», «Что изменилось за сутки»,
  «Подключить Яндекс Директ», «Переключить клиента…» (агентство).
- Вопросы на естественном языке («Почему вырос CPA?») — v1.1 вместе с «Спросить AI» в режиме чтения
  (API_CONTRACT_EXECUTION §8): ответ строится только из структурированных фактов AdPilot, с кнопками
  «Показать кампании» / «Что сделать?».

### 4.6 Состояния экранов
У каждого экрана четыре состояния: загрузка, пусто («Подключите Директ» / «Проблем не найдено — вот что проверено»),
ошибка (что случилось и что сделать, с `request_id`), данные. «Проблем не найдено» показывает, какие правила и за какой
период проверены, — отсутствие находок тоже доказательство.

### 4.7 Визуальный язык
- **Лендинг = wow:** премиальный SaaS, Liquid Glass, крупная типографика, много воздуха, глубокие градиенты, стеклянные
  превью дашборда. Обещания — только по STRATEGY: «Показываем, где рекламный бюджет расходуется неэффективно».
- **Кабинет = trust:** минимализм и ясность данных; цвет — только для статусов (факт / оценка / нет данных, свежесть,
  уровень действия), не для украшения.
- Светлая и тёмная темы; Manrope + IBM Plex Mono для цифр; мобильная нижняя навигация.
- CSP с nonce уже действует (`frontend/proxy.ts`): эффекты — CSS, без внешних скриптов и инлайновых обработчиков.

| Экран | Готов, когда |

| Настройки → Интеграции | подключения, кабинеты, свежесть и ошибки источников; цель CPA |

## 6. Вход и подключения

- Учётная запись AdPilot и подключения — разные сущности (ARCHITECTURE §7.1). Подключения Директа и Метрики — OAuth
  Яндекса, только чтение в v1.0.
- **Цель:** вход по номеру телефона + SMS-код (защита от SMS-накрутки уже в коде, `app/auth/phone.py`, флаг выключен).
  Запуск — после подтверждения юристом соответствия ст. 10 149-ФЗ (LEGAL.md).
- **До решения юриста** пилот работает на входе через Яндекс ID (`auth/login.py`) — он соответствует закону. Email —
  только контакт (чеки, биллинг), не способ входа.

## 7. Must-have v1.0 и «потом»

**v1.0 (реальный MVP):** API · реальные данные Директа и Метрики · три правила · рекомендации · статусы данных и
свежесть · решение человека и ручное выполнение · сверка и замер · история · Telegram-оповещения · вход · биллинг ·
юридический минимум (тексты, РКН) · CI, миграции, RLS, заголовки безопасности (сделано).

**Потом:** «Спросить AI» (v1.1) · API-исполнение и откат (v1.1) · квалификация лидов CSV (v1.1) · CRM, VK, другие
платформы · автоматизация по правилам (v2.0) · Outcome Graph (v2.0) · Prometheus/Grafana · расширенные E2E ·
интернационализация · SOC 2.

## 8. Контекст для AI — как правильно

В LLM уходят только обезличенные факты finding (ARCHITECTURE §2.4, AI_GOVERNANCE §2):
```json
{"facts": [
  {"id": "e1", "kind": "metric", "object": "campaign_A", "name": "spend",      "value": "48200.00", "unit": "rub"},
  {"id": "e2", "kind": "metric", "object": "campaign_A", "name": "conversions", "value": "9",        "unit": "count"},
  {"id": "e3", "kind": "metric", "object": "campaign_A", "name": "cpa",         "value": "5355.56",  "unit": "rub"},
  {"id": "e4", "kind": "setting", "name": "target_cpa", "value": "3000.00", "unit": "rub"},
  {"id": "e5", "kind": "finding", "rule": "high_cpa_target@1", "level": "review"}]}
```
- Не уходят: названия кампаний и объектов (только `campaign_A` — таблица соответствия на сервере), ID Яндекса, тексты
  запросов, логины, ПД, токены, сырой ответ API.
- Суммы — строками Decimal из `Value`; LLM не получает чисел, которых нет в фактах, и не может их ввести (валидатор).

## 9. Недели 2–3 — первый срез на этой спецификации

1. Правила `zero_conv_campaign@1` и `zero_conv_placements@1` (пороги «достаточного объёма» — в спецификации rule engine,
   предложить до начала недели 2), `high_cpa_target@1` — уже есть; golden-набор на все три.
2. `audit/exposure.py` — итог без двойного учёта (ECONOMICS.md), с тестами инвариантов.
3. `GET /workspaces/{ws}/today` по API_CONTRACT §8 на реальном снимке; `<ValueView>` и свежесть во фронтенде.
4. «Почему» по §4.3 с шаблонным текстом (LLM — после, тот же контракт).

**Готово, когда:** на реальном снимке кабинета «Сегодня» показывает итог ≈, число проблем и 3 действия; любую цифру
можно раскрыть до правила, версии и периода; ни одна цифра не выводится мимо `Value`.

## 10. Открытые вопросы

1. Пороги «достаточного объёма данных» для «Нулевых конверсий» и «Площадок РСЯ» (неделя 2).
2. Модель тарифа агентства — за кабинет или за участника (неделя 5).
3. Экспорт истории для клиента агентства — v1.0.x или v1.1.
4. Liquid Glass на лендинге — отдельная дизайн-задача; бюджет производительности с учётом динамического рендера
   (CSP nonce отключает статический кэш страниц).
