# Закрытый пилот: подготовка, включение и восстановление

Статус: локальные изменения и проверяемый план. Пилот, внешние подключения и реальные оплаты этим документом не подтверждаются. Контакт по решению владельца остаётся заглушкой, набор не объявляется открытым.

## Участники и единица сервиса

Стартовая проверяемая гипотеза: директологи и небольшие агентства с несколькими проектами Яндекс Директа. Владельцу бизнеса показываем сводку того же проекта. Это не доказанный лучший сегмент.

Подписка относится к одному workspace. 1/5/15 рекламных аккаунтов внутри workspace не означают 1/5/15 изолированных клиентов. Для раздельного доступа клиентов нужны отдельные пространства; в пилоте их выдаёт оператор. Платёжный период, действующие лимиты и право доступа берутся с backend, а не из статического прототипа. Цены публичного preview предварительные; автоматического продления нет.

## Перед первым внешним участником

1. Сохранить commit/source manifest, receipt тестов и build ID одной версии. Не включать чужие незавершённые изменения в релиз автоматически.
2. Утвердить документы, владельца сервиса, канал приглашения, scope тестовых аккаунтов и план хранения данных. До этого публичная страница явно сообщает о закрытом наборе.
3. Сверить фактическое окружение с `render.yaml`: preview имеет отключённые email/Yandex API/worker. Включать необходимые возможности по одному после утверждения соответствующего внешнего сценария. Не копировать ключи в отчёт.
4. Выполнить существующий `deploy/readiness.py` с настройками тестового окружения. PASS конфигурации не заменяет реальную доставку письма или OAuth.
5. На утверждённых тестовых аккаунтах проверить письмо → подтверждение → вход/выход → сброс пароля. Зафиксировать outcome, время и request ID, без адреса/токена/содержимого письма.
6. Отдельно проверить OAuth Директа/Метрики, отзыв доступа, выбранные аккаунты, первую синхронизацию, ошибки API и повтор после сбоя. Проверить server-side workspace boundary.
7. Проверить пригодный snapshot → аудит → объяснение/ограничения → внутреннее решение → ручное действие специалиста → read-only сверку. Никаких автоматических рекламных записей.
8. Проверить retention runner на разрешённых тестовых данных; оператор должен видеть ошибки и число обработанных записей. Не объявлять production retention исправным по одному локальному тесту.
9. Платежи оставить выключенными до отдельного допуска. После него сначала тестовый режим: checkout, повтор webhook, provider outage, отмена/возврат, отсутствие двойного продления. Успех SDK/mock не равен реальному платежу.

Каждый шаг: дата, версия, окружение, команда/сценарий, результат, путь и SHA256 артефакта, ограничение. Внешний контакт и недостающие допуски отмечаются как отсутствующие, а не заменяются выдумкой.

## Ограничения истории и наблюдаемость

Текущие пилотные защитные лимиты Intelligence на workspace:

| Запись | Новых за скользящие 24 часа | Максимум истории |
|---|---:|---:|
| Ревизия профиля | 100 | 1 000 |
| Уникальный импорт | 500 | 10 000 |
| Новый анализ | 500 | 10 000 |

Сервер сериализует резервирование workspace lock. Повтор существующего импорта/идемпотентного анализа не расходует новую запись. Дневное ограничение возвращает 429. При заполнении истории сервер тоже возвращает 429 с причиной `history_capacity`: повтор завтра не освободит место, требуется оператор. Данные автоматически не удаляются. Это сохраняет ссылки provenance и принятые решения.

Возраст хранения и удаление связанной истории требуют согласованной политики: сначала зависимости import → run → decision, экспорт/архив и проверка восстановления. До неё действует ограничение ёмкости, а не разрушительное TTL-удаление. Принятые лимиты являются инженерными defaults пилота, не результатом измерения нагрузки.

Команда `python -m scripts.product_usage --workspace ... --from-at ... --to-at ...` работает только с ролью app_rw и выдаёт агрегаты без payload/ID участников. Добавлены текущие объёмы Intelligence и время от создания workspace до первого записанного аудита. Это техническая активация, не время до признанной пользы.

Публичный webhook ограничен 120 обращениями за скользящую минуту на процесс до доступа к БД/провайдеру. Перегрузка получает 503 без подтверждения приёма, чтобы провайдер мог повторить доставку. Проверка платежа через API провайдера и идемпотентность сохранены. Несколько процессов умножают этот лимит; на периметре нужна общая защита и наблюдаемость за 503, latency, provider errors. Локальный ограничитель не заменяет защиту от распределённой нагрузки.

## Репетиция восстановления

Локальный `verify.py backend-full` создаёт отдельный синтетический PostgreSQL, запускает тесты, делает custom-format pg_dump, восстанавливает в другую БД того же кластера и сравнивает counts workspaces/audits/recommendations/intelligence. Дополнительно проверяет, что app_rw без workspace context не видит audit_runs. Кластер затем останавливается. Результат записывается в recovery-receipt.json, если все шаги прошли.

Для хостинга отдельно: проверить доступность backup, восстановить в изолированное окружение утверждённой роли, проверить версии схемы/ключей без вывода ключей, read-only вход, изоляцию, полный объём и время. Возврат к предыдущей версии приложения не должен автоматически откатывать или удалять данные. Решение о восстановлении/переключении production принимает оператор по отдельному разрешению.

## Исследование пользы и затраты

Использовать существующий `docs/PILOT_PROTOCOL.md`: предлагаемые 8–12 компаний и 4–6 недель являются планом. Таблица `pilot-observations.csv` не содержит контактов; их хранят отдельно. До результатов задаются минимально полезное сокращение времени и допустимые ограничения данных.

Для экономики заполнить `unit-economics.csv` фактическими расходами. Все денежные поля в копейках. Стоимость поддержки = секунды работы × ставка за час / 3600; переменные расходы = hosting + storage + provider + support + payment fees; contribution = фактически полученная выручка − переменные расходы. Распределение общих расходов и округление согласуются до оценки. Плановая цена, намерение купить и реальная оплата учитываются отдельно. CAC/LTV/удержание по пустой таблице не вычисляются.
