# Система контроля рекламных расходов с AI-аналитиком — PRD v1.0

> Статус: согласован (2026-09-29), обновлён под решения P0 (2026-10-02). Рабочее название проекта: `ai-direct`.
> Что входит в какую версию — канон [VERSION_SCOPE.md](VERSION_SCOPE.md); при расхождении по объёму прав он.

## 1. Суть продукта

**Позиционирование:** платформа контроля рекламных расходов с AI-аналитиком, которая показывает не просто статистику, а расход с признаками неэффективности в ₽, его причины и конкретные действия.

Собственник покупает не AI, а контроль денег, поиск неэффективных расходов, прозрачность подрядчиков и понятные действия. AI — механизм внутри.

**Оффер:** Подключите Яндекс.Директ за 2 минуты — покажем, где рекламный бюджет расходуется неэффективно.

### Четыре вопроса собственника
1. Сколько потрачено?
2. Сколько заработано?
3. Где бюджет расходуется неэффективно?
4. Что сделать сегодня, чтобы заработать больше?

### Четыре сущности
| Сущность | Что показываем |
|---|---|
| **Расход с признаками неэффективности ≈** | Оценка в ₽ за период, по источникам; одна сумма учитывается один раз |
| **Почему** | Причина простым языком + данные |
| **Можно сэкономить ≈** | Оценка в ₽ с формулой и уверенностью |
| **Что сделать** | Конкретное действие с инструкцией |

Эта идея проходит через всё: главный экран, аудит, Telegram-дайджест, рекомендации, историю решений, кнопку «Спросить AI».

### Центральная концепция: замкнутый цикл
Конкуренты дают: данные → графики → инструменты. Мы даём полный цикл, и продукт сам доказывает свою эффективность:
```
ДАННЫЕ (Директ + Метрика, позже CRM)
  → RULE ENGINE      что реально происходит
  → AI-АНАЛИТИК      объяснить проблему
  → ДОКАЗАТЕЛЬСТВА   источник + период + формула + пороги
  → РЕКОМЕНДАЦИЯ
  → ОДОБРЕНИЕ
  → ИЗМЕНЕНИЕ        v1.0: через API с предпросмотром, одобрением и откатом (или вручную — для «проверить»)
  → ПРОВЕРКА РЕЗУЛЬТАТА  через 7 дней: CPA, конверсии, «Сэкономлено ≈ …»
```
Интерфейс: **сначала ответ, потом доказательства, потом инструменты.** Не копируем кабинеты для профессионалов (Optmyzr, Adalysis) — строим понятность для собственника с глубиной по клику.

### Главный KPI продукта
Эффект для клиента в деньгах — не число пользователей и не число рекомендаций.

**v1.0: «Сэкономлено на рекламе»** — только по выполненным рекомендациям, детерминированно, `estimated`. Одна формула в PRD, коде (`high_cpa_measure@2`) и интерфейсе:
```
Сэкономлено ≈ конверсии_после × max(CPA_до − CPA_после, 0)
при условии: конверсии_после ≥ конверсии_до; окна — 7 дней до и 7 дней после выполнения
```
Показатель отвечает на вопрос: сколько стоил бы фактически полученный объём конверсий по прежней стоимости заявки и сколько он стоил по новой. Пример: CPA 5 000 → 3 500 ₽, конверсий после 20 → «Сэкономлено ≈ 30 000 ₽». Это не дополнительная выручка — поэтому не «возвращено» и не «заработано».

В интерфейсе:
```
Сэкономлено на рекламе
≈ 30 000 ₽ · Расчётный эффект · Сравнение 7 дней до и после без контрольной группы
ⓘ Снижение рекламных расходов на сопоставимый объём конверсий. Не учитывает сезонность,
  изменение спроса и другие внешние факторы.
```
Экономия и эффективность — разные утверждения. Если стоимость заявки снизилась, а заявок стало меньше, показываем честно: «Стоимость заявки снизилась на 24% · Экономия не подтверждена: заявок стало на 12% меньше» (`verdict = not_confirmed`).

Не считается сэкономленным: просто уменьшение бюджета; снижение расхода при падении конверсий; будущая или предполагаемая экономия; предполагаемая выручка; значение без достаточных данных (меньше 3 конверсий до выполнения → «Недостаточно данных для подтверждения экономии»).

Каждое значение хранит источник, периоды до и после, `calculation_type = estimated`, `data_status`, `data_sufficiency`, версию методики (`high_cpa_measure@2`) и метод замера `measurements.method`. В v1.0 метод один — `uncontrolled_before_after` (до/после без контрольной группы); `matched_control` и `experiment` зарезервированы. Условие или формула меняются только новой версией; `@1` (допуск падения конверсий 20%) сохранена лишь для воспроизводимости уже сделанных замеров.

**v2.0: «Экономический эффект»** = экономия бюджета + **расчётная ценность дополнительных конверсий** (прирост конверсий × CPA до изменения). Это оценка в терминах прежней стоимости привлечения, **не** дополнительная выручка — так и подписываем, пока нет данных о продажах. С CRM — заменяется фактической дополнительной выручкой.

## 2. Принципы работы AI (non-negotiable)

1. **Никаких выдуманных данных.** Нет данных — «Недостаточно данных» и что подключить.
2. **Каждый вывод = источник + цифры + уровень уверенности.**
3. **Факты важнее красивого ответа.** Не уверен — говорит об этом.
4. **Только реальные данные подключённых источников.**
5. **Никаких изменений в кабинете без одобрения человека.**
6. **История решений:** что рекомендовано, почему, решение, результат.
7. **Воспроизводимость каждого вывода.** Любую цифру и рекомендацию можно восстановить задним числом: цифра → источник → период → состояние данных → снимок → расчёт (версия правила) → рекомендация. Через полгода на вопрос «почему 29 сентября вы рекомендовали это?» система показывает, какие данные видела в тот момент и по какому правилу пришла к выводу.

Числа считает детерминированный код (rule engine). LLM только объясняет и формулирует и не вводит чисел, которых нет во входных данных.

### Три типа показателей
| Тип | Что это | Примеры | Как показываем |
|---|---|---|---|
| **Фактический** | Напрямую из источника | расход, клики, лиды, конверсии, CPA | число + источник |
| **Расчётный** | Формула из фактов и вводных пользователя | оценочная выручка, прогнозный ROI, расход с признаками неэффективности, «можно сэкономить», «сэкономлено» | «≈ число» + формула + исходные данные |
| **Недоступный** | Данных нет | — | «Недостаточно данных» + что подключить/заполнить |

### Контракт данных — фундамент архитектуры
Каждое число и каждая рекомендация проходят через БД → API → AI → UI → Telegram с обязательными полями. Значение без них — ошибка валидации, не отображается и не передаётся в LLM.

```
Metric / Recommendation
├── source            yandex_direct | yandex_metrika | user_input | комбинация через "+"
├── period            дата или диапазон
├── calculation_type  actual | estimated | unavailable
├── data_status       complete | partial        — загружен ли период окончательно
├── data_sufficiency  sufficient | insufficient — хватает ли данных для вывода
├── snapshot_id       снимок данных, на котором построено значение
└── rule_version      (для расчётов и рекомендаций) версия правила с порогами на тот момент
```
Снимок: `snapshot_id`, `created_at`, `data_until` (данные включительно до), источник, статус. Снимки неизменяемы — цифры не перезаписываются, появляется новый снимок. `rule_version` нужен, потому что пороги правил будут меняться, а старый вывод должен объясняться старыми порогами. Текст объяснения LLM сохраняется как был показан, не генерируется заново.

`data_status` и `data_sufficiency` — независимые оси:

| | `sufficient` | `insufficient` |
|---|---|---|
| **`complete`** | Обычный вывод | «Недостаточно данных для расчёта» |
| **`partial`** | «Данные обновляются. Предварительный расчёт» | «Данные обновляются, пока недостаточно для расчёта» |

`partial` — период ещё дозаполняется (Директ досчитывает конверсии задним числом). Инвариант: `data_sufficiency = insufficient` ⇔ `calculation_type = unavailable` ⇔ числа нет.

Примеры: `{"source": "yandex_direct", "period": "2026-09-28", "calculation_type": "actual", "data_status": "partial", "data_sufficiency": "sufficient"}` · `{"source": "yandex_direct+user_input", …, "calculation_type": "estimated", "data_status": "complete", …}`.

### Правило «вчера» и снимки данных
- Предварительные цифры никогда не выдаются как окончательные. Утренний дайджест: «Расход с признаками неэффективности ≈ 12 400 ₽ · Данные за вчера ещё обновляются».
- Дайджест, рекомендация и расчёт «Сэкономлено» хранят `snapshot_id`. На вопрос «почему утром было 12 400, а сейчас 13 100?» система показывает: «Утренний дайджест · снимок #1842 · ≈ 12 400 ₽ → Текущий расчёт · снимок #1847 · ≈ 13 100 ₽ · Причина: данные за вчера досчитались (+3 конверсии)».

### Уведомления: уточнение цифры ≠ новая проблема
Telegram реагирует на два разных типа событий:

| Событие | Когда отправляем | Пример |
|---|---|---|
| **Уточнение цифры** (досчитались данные) | Только если значимо: отклонение ≥ 10% **и** ≥ 500 ₽ (оба условия) | ⚠️ Данные за вчера обновились · Расход с признаками неэффективности: 12 400 → 13 900 ₽ (+12%) · Причина: досчитались конверсии |
| **Новая проблема** (изменилось состояние: сработало правило) | Всегда, независимо от порога изменения общей суммы | 🔴 Новая проблема · Расход с признаками неэффективности ≈ 4 800 ₽ · Открыть AdPilot |
| Незначительное уточнение | Не отправляем, только обновляем кабинет | 12 400 → 13 100 ₽ (+5,6%) |

- «И», а не «или»: иначе 100 → 120 ₽ (+20%) даст уведомление, хотя для клиента это несущественно.
- Процентный порог — настройка пользователя: 10% / 15% / 20%. Рублёвый минимум — системная настройка, меняется без релиза.
- Критические системные события (отозван токен, счётчик Метрики перестал отдавать данные, расход без конверсий по всему аккаунту) — всегда, независимо от порогов.
- **Telegram — канал оповещения, а не зеркало кабинета.** В тексте нет названий клиентов, кампаний, запросов и логинов — только сумма, тип события и ссылка; подробности — после входа в AdPilot. Недельный отчёт — тоже агрегаты без названий.

Так принцип «AI ничего не выдумывает» — техническое правило системы, а не только инструкция в промпте: LLM получает на вход только значения с этими полями и не может сослаться на то, чего нет.

### Источник каждой цифры
Клик по любой карточке/числу → источник: система, объект (кампания №, цель Метрики), период, время обновления. Пример: «Яндекс.Директ · Кампания №123 · Вчера» / «Метрика · Цель: Отправка формы».

### Источник истины
Директ и Метрика расходятся всегда (разные модели атрибуции, дата конверсии, отказы от cookies). Для каждого показателя источник истины фиксирован и показан в подсказке:

| Показатель | Источник истины | Почему |
|---|---|---|
| Расход, показы, клики, CTR, объём трафика | Директ | Биллинг — в Директе |
| Конверсии и CPA по кампаниям/фразам/площадкам | Директ (Reports API, цели Метрики, фиксированная модель атрибуции) | Только так конверсии привязаны к объектам, по которым даём рекомендации |
| Итог конверсий по сайту, поведение, доход e-commerce | Метрика | Метрика видит все визиты, не только рекламные |

Модель атрибуции выбирается один раз при подключении и указывается в источнике («Директ · цели Метрики · последний значимый переход»).

**«Почему цифры отличаются?»** — у конверсий кнопка, показывающая оба числа рядом:
```
Директ: 32 конверсии · Метрика: 29 · Разница: 3
Источник истины для рекомендаций: Директ
Возможные причины: разные модели и окна атрибуции, время обработки данных,
в Метрике учитываются все источники трафика
```

### Свежесть данных
Всегда видно, насколько данные актуальны — в шапке кабинета и на каждой важной карточке:
```
Шапка:            Яндекс.Директ ● Данные актуальны · обновлено 10:42 · Метрика ◐ Обновляется · 10:38
Карточка:         Обновлено: 14:32 · Данные до: 28 сентября 23:59 · Статус: ещё обновляются
После финализации: Данные за 28 сентября завершены · Последняя синхронизация: 14:32
```

### Уверенность рекомендации
У каждой рекомендации — **высокая / средняя / низкая** и причина с цифрами.

**Архитектурный принцип: уверенность определяет правило, не LLM.** Никаких «модель оценила уверенность в 92%». Уверенность — результат проверяемых порогов, которые видны пользователю: «Правило: минимум 7 дней и 300 кликов · Факт: 7 дней, 312 кликов, 0 конверсий → уверенность высокая».
Данных ниже порога → рекомендация не выдаётся, показываем «Недостаточно данных».

### Безопасные рекомендации
**Чем меньше фактических данных, тем меньше допустимое воздействие на кабинет.** Цель — не показать как можно больше рекомендаций, а показать только те действия, которые подтверждены данными и которые клиент может безопасно выполнить. Лучше «Недостаточно данных. Продолжаем наблюдать», чем красивая неподтверждённая рекомендация.

| Данных | Что допустимо |
|---|---|
| Нет конверсий / нечего считать | Только проверить: «За 30 дней 0 заявок при расходе 18 400 ₽. Проверьте кампанию и источники трафика». Никаких изменений ставок |
| Мало (1–2 конверсии) | Только проверить: проблема, факты, что проверить, возможные причины. Не предлагаем менять ставку, стратегию или целевой CPA |
| Средне | Изменение — на проверку человеком |
| Достаточно | Изменение — после явного подтверждения |

Изменение в кабинете не выполняется без подтверждения пользователя никогда. Решение о допустимом уровне принимает одна политика безопасности для всех правил (ARCHITECTURE.md §4.1): правило предлагает, политика может только понизить; обе версии сохраняются в выводе. Действие учитывает тип стратегии кампании: на автостратегии ручной ставки может не быть — тогда советуем изменить настройку стратегии (например, целевой CPA с X на Y), а не ставку.

Экран рекомендации — не «Снизить ставку на 15%», а:
```
Что происходит   Заявка обходится в 5 250 ₽ вместо целевых 3 000 ₽
Что сделать      Изменить настройку стратегии с X на Y
Почему           Стоимость заявки выше цели на 75%
Данные           14 конверсий за 30 дней
Риск             Средний
[Посмотреть изменение] → что сейчас · что будет · где это в Директе · ожидаемый эффект · [Подтвердить]
```

### «Почему так решил» — у каждой рекомендации
Принцип «ничего не выдумывать» — видимая функция продукта. Каждая рекомендация раскрывает доказательства (все поля берутся из контракта данных, не из LLM):
```
РЕКОМЕНДАЦИЯ: снизить ставку на 15%
Почему:       CPA = 1 840 ₽ · Целевой CPA = 1 400 ₽ · Отклонение +31%
Период:       22–28 сентября
Данных достаточно:  ✓ 487 кликов  ✓ 19 конверсий  ✓ 7 дней
Уверенность:  средняя
Источник:     Яндекс.Директ · данные на 29.09 10:42
```
LLM пишет только человеческое объяснение поверх этого блока.

## 4. Объём v1.0

Состав v1.0, v1.1 и v2.0 — канон [VERSION_SCOPE.md](VERSION_SCOPE.md) (§2–§5). Кратко: v1.0 — Директ + Метрика, аудит, рекомендации, исполнение через Direct API с предпросмотром, одобрением по риску и откатом, ручное выполнение со сверкой, агентства и роли, «Спросить AI» (только чтение), Telegram, биллинг. Автоматизация по заранее одобренным правилам, CRM и VK Реклама — v2.0.

### Путь активации
Никаких 30 настроек до первого результата. Экран после регистрации — четыре шага со статусами: «1. Подключите Директ ✓ · 2. Подключите Метрику ✓ · 3. Синхронизация данных ◐ · 4. Первый аудит · До первого аудита: примерно 2 минуты».
- **Вход и регистрация — по российскому мобильному номеру и SMS-коду** (один поток: номер новый → после кода принять оферту и отдельное согласие на обработку ПД — оба обязательны; согласие на рассылки — по желанию; без них пользователь не создаётся). Email — необязательный контакт для чеков и биллинга, не способ входа. Запуск регистрации — **HOLD до подтверждения юристом** (§10 №13, LEGAL.md). Правила кода и лимиты — API_CONTRACT §11.
- Яндекс OAuth — только для подключения Директа и Метрики, не для входа: оба подключения выполняются в рамках одного onboarding, но у каждого отдельный статус и набор разрешений.
- **В workspace можно подключить несколько кабинетов Директа.** Количество ограничивает тариф (`max_ad_accounts`), а не схема. Синхронизация, снимок и аудит идут по каждому кабинету; каждый вывод и рекомендация показывают, к какому кабинету относятся.
- До первого аудита — никаких обязательных полей. Средний чек и конверсия лида в продажу — после аудита, опционально.
- «2 минуты» — цель для небольших аккаунтов. Reports API асинхронный: на больших аккаунтах показываем прогресс и досылаем результат в Telegram.
- Логин/пароль клиента от Яндекса не получаем никогда — только OAuth-токен (шифрованный).

### Правила аудита v1.0 (кандидаты; пороги и формулы — в спецификации rule engine)
| Проблема | Формула расхода с признаками неэффективности | Действие |
|---|---|---|
| Поисковые запросы без конверсий | Σ расход по запросам с кликами ≥ N и 0 конверсий | Добавить минус-слова |
| Площадки РСЯ без конверсий | Σ расход по площадкам с 0 конверсий | Исключить площадки |
| CPA выше целевого (`target_cpa` задан клиентом) | (CPA − target CPA) × конверсии | Снизить ставку |
| CPA выше базового уровня (`target_cpa` не задан) | (CPA − baseline CPA) × конверсии | Проверить причину роста + «Укажите целевой CPA» — **без** предложения менять ставку/бюджет |
| Кампания без конверсий N дней | Σ расход за период | Остановить / проверить |
| Расход есть, конверсий 0 по всему аккаунту при прежней активности | Σ расход за период | Проверить цели и счётчик Метрики |
| Неэффективные часы/регионы | Σ расход в сегментах с 0 конверсий | Корректировки ставок |

**Одна сумма учитывается один раз.** Итог «Расход с признаками неэффективности ≈ N ₽» — не сумма карточек, а объединение затронутого расхода на самой мелкой общей единице (кабинет · кампания · объект · день) по детерминированной формуле `exposure_total@1`: вывод уровня кампании покрывает весь её расход за день, и выводы по объектам той же кампании за тот же день сверх него не добавляются; пересекающиеся измерения (например, регион и час) берутся по максимуму, а не суммой. В ответе — итог, разбивка по типам проблем и сколько вычтено как пересечение. У карточки — своя сумма и отметка, если часть уже учтена в другой карточке. «Можно сэкономить ≈» в итоге считается так же. Значение всегда `estimated` и всегда с «≈». Подробности — API_CONTRACT, DATA_MODEL.

### 4.1 Target CPA и baseline CPA
Два разных понятия — система никогда не выдаёт одно за другое:

| | `target_cpa` | `baseline_cpa` |
|---|---|---|
| Кто задаёт | клиент | система |
| Что значит | бизнес-цель: какой CPA приемлем | исторический ориентир: каким CPA был |
| Тип показателя | `user_input` | `estimated`, с формулой |
| Что может предложить правило | изменить ставку/бюджет | только «проверить причину» + предложение задать target |

- Target задан → CPA сравнивается с target: «CPA 4 800 ₽ выше целевого CPA 3 000 ₽».
- Target не задан → система **не создаёт бизнес-цель автоматически**, сравнивает с baseline: «CPA 4 800 ₽ на 34% выше вашего исторического базового уровня 3 580 ₽».
- Данных для baseline недостаточно → правило CPA не применяется, «Недостаточно данных для расчёта базового CPA».

**Две версии правил, одна проблема.** `high_cpa_target@1` (target задан) и `high_cpa_baseline@1` (target не задан) — отдельные версии в реестре с собственными параметрами, но одно семейство `high_cpa`: `issue_key` не включает ни режим, ни версию. Клиент задал target → та же проблема и рекомендация, новый вывод через `seen_again`.

**Шаг ставки `high_cpa_target@1` (зафиксирован, меняется только новой версией):**
```
delta_pct  = (current_cpa − target_cpa) / target_cpa × 100      — в Decimal, без округления
delta_pct < 10            → правило не срабатывает
steps      = floor(delta_pct / 20)
bid_change = −clamp(steps × 5%, 5%, 25%)
```
+10% → −5% · +39,99% → −5% · +40% → −10% · +66,7% → −15% · +80% → −20% · ≥ +100% → −25%.
Пороги сравниваются с точным `delta_pct`; округление до 0,1 — только для показа.

**Качество данных текущего периода** (`current_data_quality`: ≥ 10 конверсий — high, 3–9 — medium, 1–2 — low) показывается пользователю и **не запрещает действие**. Отдельно от `baseline_data_quality`; ни то ни другое не называется «уверенностью».

**Расчёт baseline CPA:**
```
baseline_cpa = Σ расход / Σ конверсий за 30 дней, предшествующих оцениваемому периоду
```
- **Отношение сумм, а не медиана дневных CPA.** Медиана по дням с конверсиями отбрасывает расход дней без конверсий — baseline систематически занижается, и правило даёт ложные срабатывания; у малого бизнеса с 2–3 конверсиями в месяц дневной CPA к тому же скачет на порядок. Отношение сумм учитывает весь расход и не даёт деления на ноль по дням.
- **Окно baseline не пересекается с оцениваемым периодом** (оцениваем последние 7 дней → baseline по дням 8–37). Иначе период сравнивается сам с собой, и рост CPA «съедается» baseline.
- **`baseline_data_quality`** по числу конверсий в окне: ≥ 20 → `high`, 10–19 → `medium`, < 10 → `insufficient` (baseline не считается). Это классификация достаточности данных для бизнес-правила, **не** статистическая уверенность — поэтому отдельное имя, не `confidence`. Пороги — часть `rule_version`: смена 20 → 30 = новая версия правила, старые аудиты сохраняют прежний смысл.
- **Источник конверсий для CPA.** Основной показатель CPA по кампаниям рассчитывается из отчёта Яндекс Директа по полям `Conversions_<goal>_<attribution_model>` и `Cost`. Эти поля основаны на данных Яндекс Метрики, но извлекаются в том же отчёте, что и расходы кампании. Отчёты Яндекс Метрики используются отдельно для проверки доступности счётчика и целей, диагностики расхождений и правил, которым требуются данные сайта. Отказ API Метрики не выключает CPA, если Директ вернул конверсии.
- **Одинаковое определение конверсии.** Baseline и текущий CPA считаются из одного снимка, с одними и теми же целями, счётчиком, моделью атрибуции и фильтрами (замороженные настройки `audit_run`). Сравнение разных определений исключено конструкцией, а не проверкой.
- **Никаких 0 и бесконечностей.** Конверсий в окне 0 или < 10 → `baseline_cpa = null`, правило `NOT_ENOUGH_DATA`. Конверсий в оцениваемом периоде 0 → CPA не определён, правило CPA не применяется (эту ситуацию ловит правило «кампания без конверсий»).
- **Требуемая история:** evaluation window 7 дней + baseline window 30 дней = **37 дней** в одном снимке. Поэтому каждая синхронизация загружает последние 37 дней (и бесплатный аудит тоже — он показывает результат за 30 дней, но грузит 37). Истории меньше 37 дней (новый аккаунт) → никакого частичного расчёта: `NOT_ENOUGH_DATA` с кодом причины `baseline_history_insufficient`. Новые статусы не вводим — причины различаются кодом (`audit_runs.rules_skipped`).
- `minimum_spend` для baseline — потом, если на данных окажется нужен.
- **Доменные автотесты:** окна не пересекаются; ноль конверсий → `null`, а не 0/Infinity; baseline не порождает действий со ставкой/бюджетом.

**Доказательство вывода (`evidence`) — полностью воспроизводимое:**
```
Rule:                 high_cpa_baseline@1
Evaluation period:    24–30 сен 2026 · расход 42 000 ₽ · конверсий 8 · CPA 5 250 ₽
Baseline period:      25 авг–23 сен 2026 (30 дней)
Baseline:             расход 115 200 ₽ · конверсий 30 · CPA 3 840 ₽
Method:               period_total_spend / period_total_conversions
Conversion definition: цели Метрики [ID…], счётчик №…, атрибуция «последний значимый переход»
Difference:           +36,7%
Baseline data quality: high
Action:               проверить причину · указать целевой CPA
Bid/budget change:    не предлагается
```

**Мягкий дрейф:** baseline со временем подтягивается к текущему уровню — это ожидаемо, он показывает отклонение от недавнего прошлого, а не от цели. Поэтому при каждом выводе по baseline показываем «Укажите целевой CPA — оценка станет точнее».

## 5. Экраны

### Информационная архитектура личного кабинета v1.0

В личном кабинете 4 раздела верхнего уровня:

1. **Сегодня** — что происходит сейчас
2. **Рекомендации** — что нужно сделать
3. **Аналитика** — почему это происходит
4. **Настройки** — как подключено и кто имеет доступ

Отдельного раздела AI в меню нет: AI вызывается кнопкой «Спросить AI» из любого раздела. Новые пункты верхнего уровня не добавляются без отдельного продуктового обоснования.

**Термины денег в интерфейсе** — коротко, по одному смыслу на метку: «Потрачено» (факт), «Расход с признаками неэффективности ≈» (оценка, всегда `estimated` и с «≈»), «Можно сэкономить ≈» (прогноз), «Сэкономлено ≈» (измерено после действия). Пояснение к оценке: «Оценка расходов, по которым система обнаружила признаки неэффективности. Одна и та же сумма учитывается в итоге только один раз». «Потеряно», «Потери», «Возвращено» и «заработано» не используем.

### 1. Сегодня
Главный экран. Отвечает на вопросы: что произошло, где бюджет расходовался неэффективно, что изменилось, что требует внимания, что предлагает сделать AdPilot, какой результат уже получен.
```
Сегодня                                  Директ ● 10:42 · Метрика ● 10:38
Потрачено 84 200 ₽ · Расход с признаками неэффективности ≈ 12 400 ₽
Можно сэкономить ≈ 8 700 ₽ · Сэкономлено ≈ 3 000 ₽
Конверсии 47

⚠ Требуют решения: 3
1. Кампания X     2. Площадка Y     3. CPA вырос
```
Элементы: Потрачено; Расход с признаками неэффективности ≈; Можно сэкономить ≈; Сэкономлено ≈; Конверсии; статус подключений и актуальности данных; изменения за последний период; активные проблемы; рекомендации, требующие решения; последние действия AdPilot. Каждая цифра — с типом показателя и источником по клику. Глубина — по клику, не на главной.

### 2. Рекомендации
Все рекомендации и вся история их обработки — не только сегодняшние. Фильтры: Все · Новые · Требуют решения · Выполненные · Отложенные · Отклонённые.

Состояния: новая · требует решения · одобрена · применена · отложена · отклонена · не выполнена · отменена.

**Паспорт рекомендации** (раскрывается по «Почему?») показывает: проблему; фактические данные; период; источник данных; расчёт; причину рекомендации; предлагаемое действие; потенциальный эффект; ограничения; проверку безопасности; решение пользователя; результат выполнения. Собственник сначала видит решение, основание, период и качество данных; формула и версия правила — в блоке «для маркетолога».

Для агентств — фильтрация и переключение между клиентскими workspace / рекламными кабинетами. У каждой рекомендации видно, к какому кабинету она относится.

**Применение через API.** Рекомендация → **предпросмотр** → одобрение → изменение → проверка выполнения → результат через 7 дней.
```
Изменение: снизить бюджет кампании на 15%
Было: 10 000 ₽/день → Станет: 8 500 ₽/день
Причина: CPA на 32% выше целевого · Источник: Яндекс.Директ · Риск: высокий
[Отмена] [Применить]
```
- Одобряется конкретная версия действия и ожидаемое текущее значение параметра из предпросмотра. Одобрение действует 24 часа. Если перед записью параметр в Директе уже не тот, что был при одобрении, изменение не выполняется: нужен новый предпросмотр и новое одобрение.
- Применение через API разрешено **только на полных данных**. Если в окне оценки есть неполные дни (конверсии ещё досчитываются), действие понижается до «проверить вручную».
- **Одобрение зависит от риска действия, а не от типа организации.** Уровень риска (`risk_policy@1`) считает код: исключить площадку или добавить минус-фразу — средний; изменение ставки или цены конверсии — средний, высокий или критический по величине изменения; изменение дневного бюджета — высокий или критический; остановка кампании или группы — критический. Сколько разных участников должны одобрить действие каждого уровня, задаёт политика одобрения workspace (по умолчанию: средний и высокий — 1, критический — 2). Пока кворум не набран — «Одобрено 1 из 2». Если одобрение пользователя завершает кворум и у него есть право исполнения — одна кнопка «Применить». Таблица уровней и правила — EXECUTION_SAFETY.md.
- Если AdPilot не умеет безопасно применить изменение для этого типа кампании или стратегии либо нет права записи — исполнения через API нет: «выполните вручную».
- **Откат:** «Вернуть назад» — 7 дней после применения, нужно право одобрения. Откат выполняется, только если параметр не менялся после применения; если менялся — «Откат перезаписал бы более новое изменение — проверьте вручную».
- Рекомендации «проверить» (данных мало) API не применяют: «Проверил» · «Позже»; после «Проверил» — «Проблема проверена. Изменений в рекламе не зафиксировано. Продолжаем наблюдение», «Сэкономлено» не считается.

История одной рекомендации:
```
12.09 · Рекомендовано: снизить ставку · Причина: CPA на 31% выше цели · Уверенность: средняя
→ Одобрено и применено 12.09 → Через 7 дней:
   CPA 1 840 ₽ → 1 420 ₽ · Конверсии 19 → 21 · Сэкономлено на рекламе ≈ 3 000 ₽
```
Итог измерения: результат измерен / экономия не подтверждена / без эффекта / недостаточно данных.

### 3. Аналитика
Анализ эффективности рекламы без захода в рекламные кабинеты. Не BI-система — ответы на вопросы собственника: куда ушли деньги, где расход с признаками неэффективности, где расходы выросли, где стало лучше.

Показывает: расходы; клики; конверсии; CPA; CTR; динамику основных показателей; изменения расходов (вчера ↔ позавчера и за период; позиции не используем); расход с признаками неэффективности; возможности экономии; данные по кампаниям — в деньгах, не в метриках.

Финансовые показатели и ROI — только при наличии источника данных и их достаточности, иначе «Недостаточно данных». Позже сюда добавляются другие платформы и CRM.

### 4. Настройки
Профиль пользователя (номер телефона, необязательный email); workspace; участники команды; роли и права; рекламные аккаунты; Яндекс Директ; Яндекс Метрика; дополнительные интеграции; уведомления; тариф и биллинг; безопасность; управление API-доступом; управление данными и удаление аккаунта. Для агентства — управление участниками команды и клиентскими workspace.

**Роли — две оси** (детали прав — API_CONTRACT §10):
- в организации: `owner` · `admin` · `member`. Owner и admin видят все workspace организации и управляют командой, интеграциями и биллингом; удалить организацию может только owner;
- в workspace: `approver` (смотреть, решать, одобрять, применять) · `analyst` (смотреть, решать, применять уже одобренное) · `viewer` (только смотреть).

`member` видит **только** те клиентские workspace, куда его добавили, — ограничение доступа агентства по клиентам входит в v1.0. Подключая Директ клиента, агентство подтверждает право передавать его данные в AdPilot и давать доступ к его кабинету (LEGAL.md).

Здоровье интеграций:
```
Яндекс.Директ  ✓ Подключён     Метрика ✓ Подключена     CRM — не подключена
Последняя синхронизация: 10:42 · Ошибок: 0
```
Ошибка синхронизации или отозванный токен → статус здесь + уведомление в Telegram + баннер на «Сегодня».

### AI-помощник — «Спросить AI»
- Не пункт меню, а кнопка, доступная из всех основных разделов.
- Контекст вопроса: текущий workspace, выбранный рекламный кабинет, период и экран, с которого открыт чат. Примеры: на «Сегодня» — «Почему вырос расход с признаками неэффективности?»; в «Рекомендациях» — «Почему AdPilot предлагает снизить ставку?»; в «Аналитике» — «Что сильнее всего повлияло на CPA за неделю?».
- AI объясняет только фактические данные и структурированные результаты системы (принципы §2). Не придумывает отсутствующие значения, метрики, причины или результаты действий. При недостаточности данных — прямо говорит об этом.
- Каждое утверждение ответа ссылается на факт из контекста; утверждение без доказательства отбрасывается, а если отброшен главный вывод — показывается шаблонный ответ, собранный кодом (AI_GOVERNANCE.md).
- **В v1.0 — только чтение.** У AI нет действий записи. Просьба «снизь ставку» → ссылка на существующую рекомендацию или «такой рекомендации нет»; изменение — только через обычный поток рекомендации. Создание запроса на действие из чата — v1.1.

### Недельный отчёт собственнику (Telegram, раз в неделю)
«За неделю реклама потратила 412 000 ₽. Найдено 8 проблем · 5 рекомендаций выполнено · Сэкономлено на рекламе ≈ 17 400 ₽. 3 проблемы требуют решения.»
Механизм удержания: продукт регулярно показывает собственнику свою пользу в ₽. В отчёте — только агрегаты, без названий клиентов и кампаний (§2, «Уведомления»).

## 6. Развитие

Что входит в v1.1 и v2.0 — [VERSION_SCOPE.md](VERSION_SCOPE.md) §4–§5. Главное в v2.0 — **режимы безопасности** (клиент наращивает доверие постепенно): только наблюдение → рекомендации → ручное применение → автоматизация по заранее одобренным правилам (открытый вопрос 8); amoCRM, Битрикс24; VK Реклама.

**Идеи без версии:** рейтинг здоровья рекламы (с разбивкой балла), AI-контроль подрядчика, настройка порогов готовых правил.

### Не делаем
Генерация креативов и лендингов, SEO, email-маркетинг, CRM, создание кампаний с нуля, прогнозирование продаж, BI-система, **визуальный конструктор правил** (перегружает продукт, требует знаний рекламщика), **десятки AI-функций** — AI сначала делает одно дело очень хорошо: понимает рекламные данные и находит проблемы.

## 7. Монетизация

**Монетизация присутствует в v1.0.** Первый аудит — бесплатно, без привязки банковской карты. Постоянный мониторинг и функции SaaS — после самостоятельного оформления подписки. Автоматическое списание после бесплатного периода без явного подтверждения запрещено.

Цель v1.0 — проверить не только «пользуются ли», но и «готов ли бизнес платить за контроль рекламных денег».

**Воронка:**
```
Сайт → Регистрация → Директ + Метрика → БЕСПЛАТНЫЙ ПЕРВЫЙ АУДИТ (реальные данные клиента, не демо)
→ «Бесплатный аудит завершён. Найдено 7 проблем. Хотите получать ежедневный контроль?»
→ «Продолжить мониторинг» → выбор тарифа → явное подтверждение → оплата
```

### Стадии пользователя
| Стадия | Кто | Доступ |
|---|---|---|
| **Visitor** | изучает сайт | — |
| **Free / Audit** | подключил аккаунт, получил первый аудит | результат первого аудита (просмотр), без обновлений |

| Тариф | Состав |
|---|---|
| **Старт** | Директ, Метрика, AI-аудит, расход с признаками неэффективности, рекомендации, Telegram, оценочная выручка и прогнозный ROI (при заполненном чеке), «Спросить AI» |

Метрика — база, не премиум: без целей и конверсий неэффективный расход не видно. Цены в ₽ — не определены.

### Тарификация агентств
Способ тарификации агентств на этапе разработки не фиксируется. Система поддерживает обе модели:
- **по клиентским рекламным кабинетам** — стоимость зависит от количества подключённых клиентов / рекламных кабинетов (в workspace их может быть несколько, лимит `max_ad_accounts`, проверка `can()`);
- **по пользователям команды** — стоимость зависит от количества участников агентства с доступом к системе.

Архитектурное требование: тариф не привязывается напрямую к пользователю или рекламному кабинету. Модель — `plan → entitlements → usage` с абстрактными лимитами (`max_workspaces`, `max_ad_accounts`, `max_members`, `max_metrika_counters`, `max_clients`, `max_api_connections`), чтобы любую из схем можно было выбрать без изменения основной структуры продукта. Тарифная модель, лимиты и правила расчёта стоимости определяются отдельно на этапе коммерческого проектирования.

### Честный биллинг (никаких тёмных паттернов)
Жалобы на неожиданные списания после триала и сложную отмену — частая проблема конкурентов. Честность в биллинге для нас — преимущество в доверии.
- Перед оплатой: тариф, сумма, что входит, дата следующего списания, кнопка «Оплатить» (`Тариф: Старт · XXXX ₽ / месяц · Входит: ✓ Директ ✓ Метрика ✓ ежедневный аудит ✓ рекомендации ✓ Telegram ✓ история · Следующее списание: 29 октября · [Оплатить]`).
- Никакого «введите карту для бесплатного периода».
- За 3 дня до списания: «Через 3 дня будет списание 4 990 ₽» (Telegram + email, если указан; канал для пользователя без email — §10 №15).
- Триал не превращается в платную подписку молча.
- «Отменить подписку» — одна понятная кнопка в кабинете, без удерживающих лабиринтов.

## 8. Техстек и данные

- Бэкенд: FastAPI · Фронтенд: Next.js · БД: PostgreSQL · Кэш/очереди: Redis · Telegram-бот
- **LLM через адаптер** (единый интерфейс). **Основная модель — YandexGPT Pro** (Yandex Cloud Foundation Models; конкретную версию фиксируем при интеграции). В v1.0 — только эта реализация; GigaChat / Claude / OpenAI добавляются в адаптер по необходимости без переписывания продукта.
- Раз LLM в РФ, AI-слой тоже размещается в РФ-контуре (логичный кандидат — Yandex Cloud). Требование обезличивания данных перед отправкой в LLM сохраняется.

### Размещение данных
**Основной контур в РФ:** пользователи, OAuth-токены (шифр.), настройки, данные CRM, персональные данные.

**AI-слой — изолированный модуль с одной точкой входа** (не отдельный сервис, ARCHITECTURE.md §1). В LLM — только обезличенные агрегаты; кампании и объекты — непрозрачными ссылками на один запрос (`campaign_A · Расход 25 000 ₽ · CPA 1 300 ₽ · Конверсии 18`), таблица соответствия ID Яндекса — только на сервере. Никогда: имена, телефоны, email, сделки, токены, ID и названия кампаний, тексты поисковых запросов. Детали минимизации и хранения — ARCHITECTURE.md §2.4–2.5.

## 9. План работ

**Коммерческие условия v1.0:** монетизация включена; бесплатно — 1 аудит на рекламный аккаунт Директа за последние 30 дней; платно — постоянный мониторинг и функционал тарифа; платёж — только с явным подтверждением, без скрытого trial и автосписания после него.

**Срок.** Исходный план MVP на 3 недели (неделя 1 — фундамент: авторизация, стадии, workspace, подключения, синхронизация, снимки, контракт данных, rule engine, аудит; неделя 2 — продукт: «Сегодня», рекомендации, «Что изменилось», свежесть, Telegram, история решений; неделя 3 — коммерческий запуск: биллинг, тарифы, бесплатный аудит, onboarding, тестирование) составлен до расширения объёма v1.0 и решений P0 — пересматривается (§10 №14). Если сроки под угрозой, первыми после запуска выходят «Почему цифры отличаются?» и недельный отчёт.

### Параллельно с первого дня (не код)
1. Заявка на доступ к API Директа.
2. Договор с платёжным провайдером.
3. Юридическая схема (юрлицо/ИП, оферта, политика обработки ПД по 152-ФЗ) и заключение юриста по входу по номеру телефона (§10 №13).
4. Договор с российским SMS-провайдером.
5. Цены — до запуска оплаты.

**Разработка не ждёт одобрения API Директа.** Адаптер Директа делается сразу с mock- и sandbox-источником; после одобрения подключаются реальные credentials и прогоняются интеграционные тесты.

**Документы** — иерархия и порядок приоритета: [VERSION_SCOPE.md](VERSION_SCOPE.md) §1.
