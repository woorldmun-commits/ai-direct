# Безопасность исполнения — Deferred to v1.1

> **Deferred to v1.1 — не реализуется и не обещается в v1.0.** В v1.0 AdPilot не изменяет рекламные кабинеты: доступ к Direct API — только чтение, изменения вносит человек вручную, AdPilot сверяет их по данным Директа и замеряет эффект (ARCHITECTURE.md §4.2, API_CONTRACT.md §6). Этот документ — спроектированный контур безопасного API-исполнения для v1.1 (решение владельца 2026-10-02, [STRATEGY.md](STRATEGY.md), [VERSION_SCOPE.md](VERSION_SCOPE.md)): права доступа, idempotency, лимиты, журнал операций, approval flow (риск → кворум), предусловие, проверка, безопасный откат. Решения D5–D8 не удалены — перенесены в v1.1. Начинаем с 1–2 обратимых действий низкого/среднего риска. Контракт API — [API_CONTRACT_EXECUTION.md](API_CONTRACT_EXECUTION.md).

> Как рекомендация становится изменением в Директе клиента и почему это изменение нельзя сделать «не то», «не тогда» или «не тем». Основа — решения D5–D8, D14 (P0, 2026-10-02). Связанные документы: [ARCHITECTURE.md](ARCHITECTURE.md) §4 (rule engine, `safety_policy`), §4.3 (исполнение, v1.1), [API_CONTRACT_EXECUTION.md](API_CONTRACT_EXECUTION.md) §2–5 (статусы, `allowed_actions`, предпросмотр, откат), [DATA_MODEL.md](DATA_MODEL.md) §8.3 (события v1.1), [ECONOMICS.md](ECONOMICS.md) (замер), [AI_GOVERNANCE.md](AI_GOVERNANCE.md) (AI не исполняет).
>
> **Что было в документах до P0** (ARCHITECTURE §4.3, API_CONTRACT_EXECUTION §5.1) и здесь только формализуется: гейт перед изменением, предпросмотр «Было → Станет» (живёт 30 минут), повторное чтение объекта перед записью и отказ с `state_changed`, идемпотентность попыток, проверка исполнения перечитыванием, откат как попытка `kind = rollback`, сверка ручного выполнения (она остаётся в v1.0 как чтение — API_CONTRACT §6.1). **Новое в P0:** реестр возможностей (D6), `risk_policy@1` и кворум одобрений вместо `approval_mode` (D5), `precondition_hash` и срок одобрения (D7), безопасный откат (D8), роли воркеров (D14).

Все компоненты этого документа детерминированы: код, версии, тесты. LLM в конвейере исполнения не участвует ни на одном шаге (AI_GOVERNANCE.md §1).

## 1. Конвейер

```
рекомендация ──▶ capability ──▶ safety ──▶ risk ──▶ approval policy ──▶ предусловие ──▶ исполнение ──▶ проверка ──▶ замер
 (rule engine)   (что умеем)   (вправе ли)  (насколько   (сколько и чьих    (то ли сейчас    (Direct API)   (перечитать)   (+7 дней)
                                            опасно)       одобрений)          в Директе)
```

| # | Шаг | Где | Вход → выход | Отказ (причина) |
|---|---|---|---|---|
| 1 | Рекомендация | `rules/`, `audit/` | снимок → `finding` с `action` (кандидат) | — |
| 2 | Capability | `execution/capabilities.py` (§2) | `action` + контекст кампании → поддерживается / нет | `capability_unsupported` (потолок `review`) |
| 3 | Safety | `audit/policy.py` (`safety_policy@N`, ARCHITECTURE §4.1) | кандидат → `action_level` | понижение уровня с `policy_reasons` |
| 4 | Risk | `risk_policy@1` (§3) | `action` + текущее значение → `risk_level` | — (неизвестное → `critical`) |
| 5 | Approval policy | `workspace_settings.approval_policy` (§4) | `risk_level` → кворум (число разных одобривших) | `second_approval_required`, `same_approver`, `role_forbidden` |
| 6 | Предусловие | предпросмотр + `precondition_hash` (§5) | текущее состояние объекта → хэш, под которым собраны одобрения | `state_changed`, `approval_expired` |
| 7 | Исполнение | `worker_execution` (§6, §9) | одобренная версия → запрос к Директу | `execution_failed` с `error_code` |
| 8 | Проверка | тот же воркер | перечитать объект → `applied_value` | `verification_status ≠ confirmed` → не `succeeded` |
| 9 | Замер | `worker/measure.py` | +7 дней → `measurement` | ECONOMICS.md §5 |

Порядок важен: capability и safety определяют, **есть ли** кнопка API-исполнения; risk и approval policy — **сколько** одобрений; предусловие — **то ли** одобряли. Каждый шаг пишет свою версию (`capabilities@N`, `safety_policy@N`, `risk_policy@N`) в вывод или событие — решение воспроизводимо (ARCHITECTURE §2.2).

## 2. Action Capability Registry (D6)

Код-реестр `execution/capabilities.py`: данные в коде, версия `capabilities@N`. Новый тип действия или новая стратегия = новая запись + тест на фикстуре Директа + новая версия. Неизвестного реестру действия AdPilot не исполняет.

### 2.1 Запись реестра

| Поле | Смысл |
|---|---|
| `action_type` | тип действия из `finding.action.type` |
| `direct_method` | метод Direct API для чтения и для записи |
| `object_type` | кампания · группа · ключевая фраза · площадка (на уровне кампании) |
| `campaign_types` | поддерживаемые типы кампаний |
| `strategies` | поддерживаемые стратегии (нормализованные, ARCHITECTURE §4.1: `manual`, `auto_cpa`, …) |
| `field` | изменяемое поле |
| `reversible` | можно ли откатить (§7) |
| `risk` | функция риска `risk_policy` (§3) |
| `precondition_fields` | что читаем и сравниваем перед записью (§5) |

### 2.2 Типы действий — кандидаты v1.1

В v1.1 входят сначала 1–2 обратимых действия низкого/среднего риска из таблицы (какие — решит владелец продукта, §11 п. 8); остальные строки — дизайн.

Имена методов и полей — по документации Direct API v5; всё, что не подтверждено на песочнице, помечено **проверить**. Имена `action_type` — рабочие; сверка с именами в коде (`decrease_bid`, `change_budget`, `pause` в `rules/domain.py`; `change_bid`, `change_target_cpa`, `change_conversion_price` в `sources/campaigns.py`) — открытый вопрос §11.

|---|---|---|---|---|
| `inspect_only` | — | — | любые | исполнения нет |
| `change_bid` | `Bids.get` / `Bids.set` (или `KeywordBids.*` — **проверить**) | ставка | ручные ставки | да |
| `change_target_cpa` | `Campaigns.get` / `Campaigns.update` (поле средней цены конверсии в стратегии — **проверить**) | целевая цена конверсии | `auto_cpa` | да |
| `change_conversion_price` | `Campaigns.get` / `Campaigns.update` (**проверить**) | цена конверсии | оплата за конверсии | да |
| `change_daily_budget` | `Campaigns.get` / `Campaigns.update` (`DailyBudget` — **проверить**) | дневной бюджет | где бюджет задан на кампании | да |

Суммы в сервисах управления Директа, по-видимому, передаются в микроединицах независимо от `returnMoneyInMicros` отчётов — **проверить**. Конвертация `Decimal` ↔ формат API — в одном месте модуля `execution/`, с тестом.

### 2.3 Когда проверяется

| Момент | Что проверяется | Нет → |
|---|---|---|
| Формирование уровня (аудит) | действие поддерживается для типа кампании и стратегии | потолок `review`, причина `capability_unsupported` в `policy_reasons` |
| Предпросмотр | всё ниже, на свежем чтении объекта | предпросмотра с кнопкой API нет, `blocked_actions` |
| Перед записью (воркер) | всё ниже, повторно | `execution_failed`, запроса на запись нет |

Проверки: тип кампании и стратегия поддерживаются · есть право записи (`write_access = granted`; права представителя / клиента агентства через `Client-Login`) · поле изменяемо · объект не архивирован и не удалён. Любое «нет» → исполнения через API нет, `blocked_actions` с `capability_unsupported`: «AdPilot не умеет безопасно применить это изменение для такой кампании — выполните вручную». «Выполнено вручную» остаётся доступным (ручной путь v1.0 со сверкой, ARCHITECTURE §4.2).

### 2.4 Ошибки Директа → причины

| Ответ Директа | Причина в AdPilot |
|---|---|
| нет прав на изменение | `write_access = denied` у подключения (видно в «Настройках») |
| нет доступа к API / ограниченная функциональность / несовместимость со стратегией | `capability_unsupported` для объекта; попытка — `execution_failed` с кодом Директа |
| прочие ошибки | `execution_failed` с `error_code` и `provider_request_id` |

Конкретные коды ошибок сервисов записи — **проверить** на песочнице; для чтения коды уже сопоставлены (ARCHITECTURE §2.6).

## 3. `risk_policy@1` (D5)

Детерминированная функция в коде; версия хранится в выводе вместе с `risk_level`. `Δ` — относительное изменение значения поля: `(target − current) / current`.

| Действие | low | medium | high | critical |
|---|---|---|---|---|
| «Проверить» (`inspect_only`) | — исполнения нет | | | |
| исключить площадку / минус-фраза | | ✓ | | |
| ставка / целевая цена конверсии / цена конверсии | | \|Δ\| ≤ 10% | 10% < \|Δ\| ≤ 25% | \|Δ\| > 25% |
| дневной бюджет | | | \|Δ\| ≤ 20% | \|Δ\| > 20% |
| остановить кампанию / группу | | | | ✓ |
| неизвестный тип | | | | ✓ |

- `low` зарезервирован: действий с записью уровня `low` сейчас нет.
- Риск ≠ безопасность. `safety_policy` решает, **можно ли** предлагать изменение (уровень `inspect_only`/`review`/`change`); `risk_policy` — **сколько одобрений** нужно, когда изменение уже допустимо. Риск не повышает и не понижает `action_level`.
- Откат — отдельное правило (§7): одно одобрение независимо от риска.

## 4. Политика одобрения и кворум (D5)

`approval_mode` (`single_step` / `two_step` по `organizations.kind`) **убирается**. Цепочка: действие → `risk_level` → `approval_policy` workspace → требуемое число одобрений и роли → исполнение.

### 4.1 `approval_policy` (в `workspace_settings`)

| `risk_level` | Одобрений по умолчанию | Кто меняет |
|---|---|---|
| `medium` | 1 | owner / admin организации |
| `high` | 1 | owner / admin |
| `critical` | 2 | owner / admin; снизить до 1 — только явным действием **owner**, событие в журнале |

- Считаются одобрения **разных** пользователей с правом approve (ws-роль `approver` или org-роль `owner` / `admin`, D3 — ARCHITECTURE §7.2).
- Засчитываются только одобрения с одним и тем же `precondition_hash` (§5) и не истёкшие (§5.3).
- Изменение политики не затрагивает уже начатое исполнение; для ожидающих кворума действует политика на момент проверки кворума — **открытый вопрос** §11.

### 4.2 Состояния

```
requires_decision ──approve (1 из N)──▶ requires_decision «одобрено 1 из 2»
        │                                      │ approve другого участника, тот же precondition_hash
        └──approve (кворум набран)─────────────┴──▶ approved ──apply──▶ execution_started ──▶ applied / failed
```

| Ситуация | `status` | UI | `blocked_actions` |
|---|---|---|---|
| одобрений меньше кворума | `requires_decision` | «Одобрено 1 из 2» | `apply`: `second_approval_required` — «Нужно второе одобрение: критичное изменение» |
| тот же пользователь пытается одобрить второй раз | `requires_decision` | — | `approve`: `same_approver` — «Второе одобрение должен дать другой участник» |
| кворум набран | `approved` | «Одобрена» | — |

- **«Применить» (`approve_and_apply`)** доступна, когда одобрение этого пользователя **завершает кворум** и у него есть право execute. Иначе — `approve`, затем `apply` (отдельным действием, тем же или другим пользователем с execute).
- Одобрение одного человека — событие `approval_granted` (`actor_user_id`, `finding_id`, `precondition_hash`, ожидаемое состояние в `payload`). Когда кворум набран, в той же транзакции пишется системное событие `approved` (`actor_user_id IS NULL`, засчитанные одобрения в `payload`) — DATA_MODEL.md §4 `recommendation_events`. По умолчанию второе одобрение нужно только для `critical` (§4.1).

## 5. Предусловие исполнения (D7)

Формализует сверку с предпросмотром из ARCHITECTURE §4.3 / API_CONTRACT_EXECUTION §5.1.

### 5.1 Что фиксирует одобрение
```json
{"object_ref": {"type": "campaign", "id": "…"}, "field": "daily_budget",
 "expected_current_value": "…", "action": "change_daily_budget", "target_value": "…"}
```
- Значения берутся из предпросмотра (`before` → `expected_current_value`, `after` → `target_value`).
- `precondition_hash` — хэш канонической сериализации этой структуры. Повторный предпросмотр с тем же текущим значением даёт тот же хэш, поэтому второй участник может одобрить по своему предпросмотру.
- Одобрения засчитываются в кворум, только если `precondition_hash` совпадает.

### 5.2 Перед записью
Воркер заново читает объект (`precondition_fields` из реестра):

| Результат чтения | Действие |
|---|---|
| значение = `expected_current_value` | запись (§6) |
| значение ≠ `expected_current_value` | записи нет, `execution_failed` с `state_changed`; рекомендация возвращается в `requires_decision`; нужен новый предпросмотр и новое одобрение (собранные одобрения не засчитываются — хэш другой) |
| объект недоступен / архивирован | `execution_failed` с `capability_unsupported` |

### 5.3 Сроки

| Что | Срок | Истёк → |
|---|---|---|
| Предпросмотр | 30 минут (как сейчас) | новый предпросмотр; одобрение по истёкшему — `409` (код — API_CONTRACT) |
| Одобрение | 24 часа | каждое `approval_granted` истекает отдельно (`created_at` + 24 ч); истёкшее в кворум не входит; исполнение после срока → `approval_expired`, нужно новое одобрение |

## 6. Исполнение и проверка

### 6.1 Гейт перед каждым запросом на запись (воркер, не только API-роут)

| # | Условие | Причина отказа |
|---|---|---|
| 1 | последняя версия вывода = одобренная | `version_outdated` |
| 2 | данные версии `complete` | `data_partial` |
| 3 | `action_level = change` | `level_not_change` |
| 4 | capability (§2.3) | `capability_unsupported` |
| 5 | подключение `connected`, `write_access = granted` | `write_access_missing` |
| 6 | workspace активен, тариф разрешает `api_execution` | `entitlement_exceeded` |
| 7 | кворум по `risk_level` набран одобрившими с approve-правом | `second_approval_required` |
| 8 | одобрения не истекли | `approval_expired` |
| 9 | текущее значение = `expected_current_value` | `state_changed` |

Пункты 1–3, 5–6 были в ARCHITECTURE §4.3; 4, 7–9 — P0. Любое «нет» → `execution_failed` с причиной, запроса на запись к Директу нет.

### 6.2 Попытка
- Строка `execution_attempts` (DATA_MODEL §4) с UNIQUE `idempotency_key`: повтор задачи или двойной клик второго изменения не делают.
- Хранит `before` (прочитано непосредственно перед записью) и `applied_value` (подтверждено перечитыванием после записи; D8) — DATA_MODEL.md §4 `execution_attempts`.
- Ответ Директа неясен (таймаут) — не повторяем вслепую: перечитываем объект и по факту пишем `succeeded` или `failed`.

### 6.3 Проверка
После записи объект перечитывается. `execution_succeeded` (+ `verification_status = confirmed`) — только если прочитанное значение = `target_value`; оно и есть `applied_value`. Иначе — `execution_failed`.

### 6.4 Состояния попытки

```
created ──гейт──▶ started ──запись──▶ verifying ──перечитано = target──▶ succeeded
   │                │                     └──≠ target / неясно──────────▶ failed
   └──гейт «нет»────┴───────────────────────────────────────────────────▶ failed (error_code)
```
Попытка неизменна (append-only): повтор после ошибки — новая строка с новым ключом.

## 7. Безопасный откат (D8)

| Условие | Значение |
|---|---|
| Что откатываем | только `kind = apply` с `succeeded` и `reversible = true` |
| Срок | 7 дней после исполнения |
| Право | approve; **одно** одобрение (`rollback_requested`) независимо от риска исходного действия |
| Гейт | ниже; **не** требует, чтобы последняя версия вывода была одобренной: ежедневный аудит создаёт новые версии, и такой пункт блокировал бы откат |
| Идемпотентность | новая попытка `kind = rollback`, `rollback_of`, свой `idempotency_key` |

Гейт отката (воркер, перед записью): есть успешное исполнение через API (`kind = apply`, `succeeded`) · не прошло 7 дней · текущее значение == `applied_value` · у инициатора право approve · подключение `connected` и `write_access = granted` · capability поддерживает обратное изменение (`reversible`, проверки §2.3 на свежем чтении). Любое «нет» → записи нет: `rollback_blocked` (значение изменилось) или `rollback_failed` с причиной.

```
перечитать объект ──▶ текущее == applied_value ? ──да──▶ записать before ──▶ перечитать ──▶ rollback_succeeded
                                     └──нет──▶ записи нет, rollback_status = blocked
```
- `blocked`, причина `state_changed_since_execution`: «С момента применения параметр изменился (сейчас X). Откат перезаписал бы более новое изменение — проверьте вручную». Значения `rollback_status` — API_CONTRACT_EXECUTION §2.
- Успешный откат исключает замер из «Сэкономлено» (API_CONTRACT_EXECUTION §5.3).

## 9. Роли воркеров (D14)

Логическое разделение с отдельными учётками БД и очередями. Может быть один процесс arq, но разные DSN/роли по семействам задач: процесс с доступом к токену не получает прав на удаление, биллинг и т. п. **[v1.0]** — семейства `worker_sync`, `worker_ai`, `worker_billing`, `worker_notify`, `worker_deleter` (в документах; роли БД — в PR воркеров). `worker_execution` — **[v1.1]**: в v1.0 его нет, сверка ручного выполнения (чтение) — в `worker_sync`.

| Воркер | Задачи | Токен Директа/Метрики | Пишет | Не может |
|---|---|---|---|---|
| `worker_sync` | синхронизация, снимки, аудит; **[v1.0]** сверка ручного выполнения (чтение) | читает | снимки, `stat_rows`, выводы | исполнять изменения, удалять, биллинг |
| `worker_ai` | объяснения; «Спросить AI» — [v1.1] | **нет** | `explanations` | видеть токены, названия, тексты запросов (только обезличенные агрегаты) |
| `worker_execution` **[v1.1]** | предпросмотр, исполнение, откат | читает | `execution_attempts`, события исполнения | удалять, биллинг, писать снимки |
| `worker_billing` | продление, списания, сверка | нет | подписки, платежи | токены рекламы |
| `worker_notify` | доставка outbox, email-дайджест | нет | `notifications` | токены, исполнение |
| `worker_deleter` | удаление, ретеншн | нет | только через функции удаления (`app_deleter`, ARCHITECTURE §2.3) | всё остальное |

Сейчас (ARCHITECTURE §2.3) роль `app_token` — одна на весь воркер. Задачи одного workspace — под `app_rw` / `app_token` с `app.workspace_id` (RLS, D13); задачи по многим workspace (планировщик, outbox, уведомления, выбор замеров) — под `app_system`; удаление и ретеншн — функции `SECURITY DEFINER` под `app_deleter`.

## 10. Тесты [v1.1]

- Реестр: действие вне реестра или неподдерживаемая стратегия → потолок `review` и `capability_unsupported`; запроса к Директу нет.
- `risk_policy@1`: таблица граничных значений (10%, 25%, 20%) → ожидаемый `risk_level`; неизвестный тип → `critical`.
- Кворум: `critical` при умолчаниях требует двух разных пользователей; повтор того же — `same_approver`; одобрения с разным `precondition_hash` не складываются; снижение `critical` до 1 — только owner, событие в журнале.
- Предусловие: изменённое значение → `state_changed`, возврат в `requires_decision`; одобрение старше 24 ч → `approval_expired`.
- Откат: значение изменилось после исполнения → `blocked`, записи нет; через 7 дней — недоступен; повтор — без второго изменения; новая версия вывода после исполнения откат не блокирует.
- Роли воркеров: DSN `worker_ai` не читает токен (ошибка прав БД).
- Идемпотентность, неясный ответ API. Ручное выполнение без сверки не `confirmed` — тест v1.0 (ARCHITECTURE §11).
- **[v1.0]** Сборка v1.0 не вызывает методы записи Direct API (тест allowlist методов клиента Директа, ARCHITECTURE §11).
