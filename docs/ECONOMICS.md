# Экономика выводов — v1.0

> Какие денежные суммы показывает AdPilot, как они называются, как считается итог без двойного счёта и как замеряется эффект. Основа — решения D9, D10 (P0, 2026-10-02). Связанные документы: [PRD.md](PRD.md) §1 «Главный KPI», §4 (правила), [ARCHITECTURE.md](ARCHITECTURE.md) §3 (`Value`), §4, §5, [API_CONTRACT.md](API_CONTRACT.md) §7–8, [DATA_MODEL.md](DATA_MODEL.md) §4, [AI_GOVERNANCE.md](AI_GOVERNANCE.md) §4 (гейт).
>
> Все суммы — `Decimal`, рубли с двумя знаками, всегда через `Value` (`calculation_type = estimated`, с `formula` и версией). Считает детерминированный код; LLM чисел не вводит.

## 1. Термины

| В UI | Смысл | В коде / БД | В API | Тип |
|---|---|---|---|---|
| **«Расход с признаками неэффективности ≈ N ₽»** | оценка расходов, по которым система обнаружила признаки неэффективности | `findings.lost` (= exposure) | `exposure` | всегда `estimated`, всегда «≈» |
| «Можно сэкономить ≈ N ₽» | прогноз эффекта действия, своей формулой | `findings.recoverable` | (API_CONTRACT) | `estimated` или `unavailable` |
| «Сэкономлено ≈ N ₽» | расчётный эффект выполненного действия | `recommendation_results.saved` | `measurement.saved` | `estimated` |

- Было: «Потеряно / Потери ≈». Новый термин — везде: UI, PRD, лендинг, Telegram. Пояснение рядом с итогом: «Оценка расходов, по которым система обнаружила признаки неэффективности. Одна и та же сумма учитывается в итоге только один раз».
- Лендинг: «Показываем, где рекламный бюджет расходуется неэффективно» (вместо «узнайте, где теряются деньги / сколько потеряли»).
- **38-ФЗ.** Ст. 5 требует достоверности рекламы. Осторожный термин и «≈» — **наша мера снижения риска** вводящих в заблуждение утверждений, а не дословное требование закона.
- Внутренние имена (`lost`) в коде и БД в этом PR не переименовываются; в DATA_MODEL — пометка «`findings.lost` = exposure».
- «Возвращено» и «заработано» не пишем (API_CONTRACT §7).

## 2. Сумма карточки и итог

- **Карточка** (вывод) показывает свою сумму — `lost` своего правила (формулы — PRD §4). Если часть её расхода уже учтена в другой карточке, у карточки отметка «частично учтено в другой карточке».
- **Итог** («Сегодня», недельный отчёт, Telegram) — **не сумма карточек**, а `exposure_total@1` (§3). Карточки разных правил могут описывать один и тот же рубль: кампания без конверсий и запросы без конверсий внутри неё.

## 3. `exposure_total@1` — итог без двойного счёта

Код: `audit/exposure.py`, чистая функция без I/O; не импортирует `ai/`. Вход — выводы последнего аудита по каждому кабинету workspace (кабинетов N, D4) и строки `stat_rows` их снимков.

### 3.1 Единица
Самая мелкая общая единица — **кабинет · кампания · объект · день** (из `stat_rows`: `direct_account`, `campaign_id`, `object_id`, `date`). Кабинет в единице — поэтому кампании разных кабинетов никогда не сливаются.

### 3.2 Покрытие вывода

| Уровень вывода | Какие единицы покрывает |
|---|---|
| объект (запрос, площадка, сегмент) | свои единицы: объект × дни окна оценки |
| кампания | **весь** расход кампании за каждый день окна оценки |
| кабинет («0 конверсий по всему аккаунту») | все кампании кабинета за каждый день окна |

У вывода, чья сумма — сумма расхода по единицам («без конверсий»), вклад единицы = её `cost`. У вывода с формулой (`(CPA − target) × конверсии`) сумма на единицы не раскладывается — он участвует блоком «кампания × дни окна» со своей суммой.

### 3.3 Алгоритм
Для каждой пары кабинет · кампания:

1. **Объектные выводы.** Объединение их единиц; каждая единица — один раз (два вывода по одному объекту за один день не удваивают его расход).
   Измерения, которые могут пересекаться (например, регион и час — когда появятся), по одной кампании за один день берутся **по максимуму**, а не суммой. Запросы (поиск) и площадки (сети) складываются как непересекающиеся — **проверить** на живых данных.
2. **Выводы уровня кампании.** Если их несколько — по максимуму (они описывают один и тот же расход).
3. **Сведение.** В дни, покрытые выводом кампании: `max(сумма вывода кампании, объектные выводы за эти дни)` — объектные выводы **сверх** вывода кампании не добавляются. В остальные дни — объектные выводы как есть.
4. Вклад пары не больше расхода кампании за эти дни.

Затем то же уровнем выше: вывод уровня кабинета против суммы вкладов его кампаний — по максимуму. Итог — сумма по кабинетам.

> Шаг 3 берёт максимум, а не всегда сумму вывода кампании: у формульного вывода (высокий CPA) сумма может быть меньше суммы объектных выводов внутри кампании, и итог не должен становиться меньше самой большой карточки (гейт §3.5). У вывода «кампания без конверсий» сумма = весь расход кампании, и максимум всегда — он.

### 3.4 Ответ
```json
{"total": "Value", "components": [{"issue_type": "…", "amount": "Value"}], "overlap": "Value",
 "version": "exposure_total@1", "formula": "Σ по кабинетам max(...)"}
```
- `components` — суммы карточек по типам проблем (до вычета пересечений).
- `overlap = Σ components − total` — сколько вычтено как пересечение.
- `total`, `overlap` — `estimated`, с формулой и версией; точная форма — API_CONTRACT.

### 3.5 Инварианты (проверяются golden evals, AI_GOVERNANCE §4.2)
- `max(карточка) ≤ total ≤ Σ карточек`.
- `overlap ≥ 0`.
- Перестановка выводов во входе не меняет результат.
- Один и тот же вход → тот же `total` (воспроизводимость, ARCHITECTURE §2.2).

### 3.6 «Можно сэкономить» в итоге
Тем же способом: вывод уровня кампании заменяет объектные выводы той же кампании за те же дни (по максимуму), пересекающиеся измерения — по максимуму. Карточки с `recoverable = unavailable` в итог не входят; если такие есть — у итога отметка «оценка есть не для всех карточек». Площадки РСЯ без конверсий (`zero_conv_placements@1`): `recoverable = unavailable` (`no_forecast`) — после исключения площадок Директ перераспределяет бюджет, модели перераспределения в v1.0 нет. Как раскладывать `recoverable` по дням для частичного пересечения окон — **открытый вопрос** §6.

## 4. Пример (иллюстративные числа)

Пример показывает алгоритм и на правилах-кандидатах (запросы, часы, регионы), которых нет среди трёх правил v1.0 (нулевые конверсии, высокий CPA, площадки РСЯ — STRATEGY.md); golden-кейсы v1.0 строятся только по трём правилам (AI_GOVERNANCE §4.1).

> **Пример, не данные клиента.** Один кабинет, окно оценки 7 дней. Числа подобраны для проверки арифметики.

| # | Карточка | Уровень | Кампания | Сумма, ₽ |
|---|---|---|---|---|
| 1 | Кампания без конверсий 7 дней (расход за окно) | кампания | A | 21 000.00 |
| 2 | Поисковые запросы без конверсий | объект | A | 4 600.00 |
| 3 | Площадки РСЯ без конверсий | объект | B | 8 300.00 |
| 4 | CPA выше целевого: (4 820 − 3 000) × 19 | кампания | B | 34 580.00 |
| 5 | Поисковые запросы без конверсий | объект | C | 3 200.00 |
| 6 | Часы без конверсий (день 1: 700, день 2: 300) | объект, измерение «час» | D | 1 000.00 |
| 7 | Регионы без конверсий (день 1: 400, день 2: 900) | объект, измерение «регион» | D | 1 300.00 |

**Σ карточек** = 21 000 + 4 600 + 8 300 + 34 580 + 3 200 + 1 000 + 1 300 = **73 980.00 ₽**.

| Кампания | Расчёт | Вклад, ₽ |
|---|---|---|
| A | вывод кампании покрывает все дни: max(21 000, 4 600) | 21 000.00 |
| B | max(34 580, 8 300) | 34 580.00 |
| C | вывода кампании нет: 3 200 | 3 200.00 |
| D | час и регион пересекаются → по дням максимум: max(700, 400) + max(300, 900) = 700 + 900 | 1 600.00 |

**total** = 21 000 + 34 580 + 3 200 + 1 600 = **60 380.00 ₽**.
**overlap** = 73 980 − 60 380 = **13 600.00 ₽** (= 4 600 карточки 2 + 8 300 карточки 3 + 700 пересечения часов и регионов в D).
Проверка инвариантов: max карточка 34 580 ≤ 60 380 ≤ 73 980 ✓. Для кампании B: расход за окно при CPA 4 820 ₽ и 19 конверсиях = 91 580 ₽ ≥ вклада 34 580 ✓.

`components`: «кампания без конверсий» 21 000.00 · «запросы без конверсий» 7 800.00 (4 600 + 3 200) · «площадки без конверсий» 8 300.00 · «высокий CPA» 34 580.00 · «часы» 1 000.00 · «регионы» 1 300.00 — в сумме 73 980.00.
Отметки: карточки 2 и 3 — «учтено в другой карточке», 6 и 7 — «частично учтено в другой карточке».

UI: «Расход с признаками неэффективности ≈ 60 380 ₽».

## 5. Замер эффекта — метод (D10)

| `measurements.method` | Статус | Смысл |
|---|---|---|
| `uncontrolled_before_after` | **v1.0, единственный** | сравнение 7 дней до и 7 после дня выполнения, без контрольной группы |
| `matched_control` | зарезервирован | сравнение с похожими кампаниями без изменения |
| `experiment` | зарезервирован | эксперимент Директа / разделение трафика |

- `method` — дизайн сравнения; `policy` (`high_cpa_measure@2`) — формула. Формула прежняя (ARCHITECTURE §5, PRD §1): `saved = конверсии_после × (CPA_до − CPA_после)` при условиях методики; любое сомнение — `saved = NULL`.
- Подпись в UI под «Сэкономлено ≈»: «Расчётный эффект · Сравнение 7 дней до и после без контрольной группы».
- Ограничение метода, которое мы честно показываем: без контрольной группы сезонность, действия конкурентов и другие изменения в кабинете неотличимы от эффекта рекомендации. Поэтому «Сэкономлено» — `estimated` и «≈».
- В «Сэкономлено» входит только подтверждённое выполнение: в v1.0 — ручное со сверкой `verification_confirmed` (API_CONTRACT §7); в v1.1 — и исполнение через API без успешного отката (API_CONTRACT_EXECUTION §5.3, EXECUTION_SAFETY §7).

### 5.1 Методики замера

Код: `app/audit/measurement.py` (чистые функции, `Decimal`, без I/O), выбор по имени `measurements.policy` — `measure(policy, …)`; воркер — `app/worker/measure.py`. Общее для всех:

- Метод `uncontrolled_before_after`: окна 7 дней до и 7 дней после дня выполнения, сам день — ни в одном окне (окна фиксирует БД при `done`).
- Окончательные данные: окно «после» должно выйти из окна дозачёта конверсий; ждём до 14 дней после окна, дальше — `insufficient` (`no_data_for_window`). Другое определение конверсии в снимке замера — `insufficient`.
- Конверсии неизвестны хотя бы за один день окон (Метрика не подключена) — `insufficient` (`conversions_unknown`): ноль не выводится из отсутствия. Кампания остановлена (расход «после» = 0) — `insufficient` (`no_activity_after`): остановка — не эффект действия.
- `saved` есть только у `verdict = effect`. «Изменение есть, экономия не подтверждена» — `not_confirmed`, наблюдаемые изменения и причина — в `effect`. Любое сомнение — `saved = NULL`.
- Вход в сумму «Сэкономлено ≈» решается отдельно и в момент показа (`counted_saved`): `execution_mode = manual` (в v1.0 — каждое `done`) **и** `verification_status = confirmed`. Сверка может прийти позже замера — тогда меняется только сумма, сам замер не пересчитывается.
- Версия — в имени. Имя ставит триггер `create_measurement_on_done`: `<issue_type>_measure@2` для любого семейства. У `zero_conv_*` это первая версия методики («@1» у них нет).

| Методика | Проблема → действие | `saved` (estimated, период — окно «после») | Условия `saved` |
|---|---|---|---|
| `high_cpa_measure@2` | высокий CPA → снизить ставку | `конверсии_после × (CPA_до − CPA_после)` | CPA снизился; `конверсии_после ≥ конверсии_до`; `конверсии_до ≥ 3` |
| `zero_conv_campaign_measure@2` | расход без конверсий → проверить цели, стратегию, запросы | `расход_до − расход_после` | см. ниже |
| `zero_conv_placements_measure@2` | площадки РСЯ без конверсий → исключить | `P_до − P_после` (расход **исключённых** площадок) | см. ниже |

**`zero_conv_campaign_measure@2`.** «Конверсии не упали» при 0 → ≥ 0 выполняется всегда, поэтому нужен дополнительный критерий. `saved = расход_до − расход_после`, только если все условия:
1. в окне «до» конверсий 0 (иначе проблемы в окне сравнения нет — `insufficient`, `conversions_before`);
2. расход снизился;
3. после — конверсии > 0;
4. `CPA_после ≤ 1 × ориентир CPA` выполненного вывода (`target_cpa` или baseline-CPA из его `evidence`, не текущие настройки).

Почему так: расход мог снизиться от урезанного бюджета, а деньги — всё так же уходить впустую (условие 3); одна конверсия на 30 000 ₽ при ориентире 3 000 ₽ — всё ещё неэффективный расход (условие 4). Эффективный расход «после» из `saved` не вычитается — консервативно. Ветки без `saved`: расход ниже, конверсий нет — `not_confirmed` (`spend_lower_still_no_conversions`); конверсии появились, расход не ниже — `not_confirmed` (`conversions_appeared_spend_not_lower`); CPA выше ориентира — `not_confirmed` (`cpa_after_above_reference`); ориентира нет (порог правила был абсолютным) — `not_confirmed` (`no_reference_cpa`); конверсий нет и расход не ниже — `no_effect`.
> В v1.0 действие этого правила — «проверить» (`inspect_only`): БД не пускает `done`, замер не создаётся. Методика готова на случай, когда действие станет выполнимым.

**`zero_conv_placements_measure@2`.** `P` — расход площадок из `action.placement_ids` выполненного вывода, `C` и `V` — расход и конверсии кампании. `saved = P_до − P_после`, только если все условия:
1. `P_до > 0` и `P_после < P_до` (исключили не всё — засчитывается только реальное снижение);
2. `V_после ≥ V_до` при `V_до ≥ 3` (иначе «не упали» ничего не проверяет — `insufficient`);
3. `C_после ≤ C_до − (P_до − P_после)`: расход кампании не вырос сверх освободившейся суммы. Иначе бюджет перетёк на другие площадки или поиск — `not_confirmed`, `budget_reallocated`, `saved = NULL`; перетёкшая сумма — в `effect.reallocated`. Частичная экономия (`C_до − C_после`) не засчитывается: снижение расхода кампании нельзя приписать исключению.

В снимке замера нет отчёта площадок — `insufficient` (`placements_not_in_snapshot`): «площадки не тратили» не выводится из того, что их не смотрели.

**Утверждает владелец продукта** (до утверждения — как есть, изменение = новая версия методики): для `zero_conv_campaign` — условия 1–4 и множитель ориентира 1; для `zero_conv_placements` — порог `V_до ≥ 3`, требование `V_после ≥ V_до` без допуска и условие 3 без допуска на шум расхода; для обеих — что остановка кампании даёт `insufficient`, а не экономию.

## 6. Открытые вопросы

1. **Запросы и площадки** — действительно ли не пересекаются по расходу в отчётах Директа (поиск vs сети); до проверки — складываются (§3.3).
2. **Выводы уровня группы** (`adgroup`), если появятся: группа содержит запросы — вероятно, обрабатывать как промежуточный уровень между кампанией и объектом, по тому же правилу максимума. Не решено.
3. **`recoverable` в итоге** при частичном пересечении окон оценки (§3.6).
4. **Окна оценки разной длины** (например, «кампания без конверсий N дней» и 7-дневные правила) — покрытие по дням это поддерживает; подтвердить на golden-кейсе.
5. **Итог по нескольким кабинетам** — показывать ли разбивку по кабинетам на «Сегодня» (D4 требует, чтобы карточки несли кабинет; про итог — не решено).
6. **Расход с НДС или без** (DATA_MODEL §11, п. 1) — влияет на все суммы этого документа.
