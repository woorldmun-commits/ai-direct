# Команда проекта INROU

Это рабочие профили для поручений в IDE и ручной координации. Они **не запускают фоновые процессы**, не подключают LLM и не являются автономными сотрудниками внутри SaaS. Руководитель интеграции выбирает нужные роли под задачу; запуск всех ролей на любую правку не требуется.

## Иерархия

Владелец продукта → руководитель интеграции → профильные исполнители → QA → независимый [Evidence Supervisor](supervisor.md). Финальный приёмочный вердикт проверяющего обязателен; выпуск и внешние действия разрешает человек. Проверяющий не может сам расширить полномочия команды.

## Запуск в Claude Code

Каждый профиль подключён как субагент в `.claude/agents/inrou/`: `inrou-backend-metrics`, `inrou-integrations-data`, `inrou-frontend`, `inrou-seo`, `inrou-security`, `inrou-legal`, `inrou-qa`, `inrou-product`, `inrou-release-ops` и главный `inrou-supervisor`. У каждого исполнителя своя зона записи (таблица — в `supervisor.md` агента); зоны не пересекаются. Общие файлы (`backend/db/schema.sql`, `backend/migrations/`, `auth/`, остальное `api/`, `tenancy.py`, lock-файлы) меняет только руководитель интеграции. Цикл: исполнитель → передача → `inrou-supervisor` → вердикт → владелец решает о коммите.

## Общие правила и формат передачи

1. Вход: задача, разрешённые файлы, исходное состояние/commit или хеши, критерии, ограничения, источники, зависимости.
2. Изменения: один писатель на worktree; остальные работают в изолированных деревьях. Чужие изменения не откатывать.
3. Каждый вывод помечать `fact`, `estimate`, `hypothesis` или `unavailable`. Ноль не означает отсутствие данных. Числа только из `Value` и детерминированного расчёта.
4. Передача: `scope`, `revision`, `changed_files`, `claims`, `evidence`, `checks`, `not_checked`, `risks`, `owner_action`.
5. Проверка: команда, cwd, версия исходников, код выхода, путь и SHA256 артефакта, время. Скриншот не доказывает реальный платёж; pytest не доказывает UX; совпадение числа не доказывает причинность.
6. Ни один профиль не имеет права: публиковать без разрешения, расходовать деньги, менять рекламу, читать production/ПД/секреты или отправлять их модели, самовольно расширять полномочия.
7. Неизвестные требования → BLOCKED с конкретным недостающим входом. Исправимая ошибка → NEEDS_WORK. PASS действует только внутри проверенного scope и версии; он не равен готовности всего продукта.

## Детерминированные функции продукта

Новые имена профилей не заменяют существующие модули:

- Контроль данных: `sources/`, `sync/`, существующие статусы подключений и свежести.
- Поиск и приоритет: `rules/`, `audit/`, существующие методики и golden evals.
- Объяснение: только факты выбранной рекомендации; до подключения проверенного LLM — шаблоны. Документ AI_GOVERNANCE сам по себе не доказывает наличие AI-адаптера.
- Сводка и повторная проверка: существующие worker/measurement/notification механизмы; никакой выдуманной экономии.

Дополнительный offline gate: `backend/app/agents/`. Он проверяет **структурированные** Value-утверждения относительно независимо подготовленного manifest, не вычисляет новые метрики и не анализирует произвольный текст. Действующий runtime автоматически на этот gate не переведён.

Запуск из `backend`: `python -m app.agents verify claims.json --evidence trusted-manifest.json`.

JSON Schema: `python -c "import json; from app.agents.supervisor import Submission; print(json.dumps(Submission.model_json_schema()))"`; аналогично `Manifest`. Формат и доверительная граница — в [контракте](../handoffs/project-agents-contract.md).
