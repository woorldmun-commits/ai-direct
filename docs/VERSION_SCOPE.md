# Объём версий AdPilot — канон

> Решения P0 (D1–D18) приняты владельцем продукта 2026-10-02; объём v1.0 пересмотрен решением 2026-10-03 — [STRATEGY.md](STRATEGY.md) (TRUTH FIRST, AI-аналитик read-only в v1.0, три сегмента, главный экран «Анализ»). Этот файл — главный перечень границ: **что входит в какую версию**. Другие документы описывают, *как* это устроено, и на объём ссылаются сюда.

Специализированные документы детализируют темы и подчиняются цепочке выше: [PRODUCT_SPEC.md](PRODUCT_SPEC.md) (пять принципов как требования, UX-паттерны и критерии готовности экранов v1.0), [EXECUTION_SAFETY.md](EXECUTION_SAFETY.md) (контур исполнения, **v1.1**), [AI_GOVERNANCE.md](AI_GOVERNANCE.md), [ECONOMICS.md](ECONOMICS.md), [DISASTER_RECOVERY.md](DISASTER_RECOVERY.md), [LEGAL.md](LEGAL.md).

**Выжимки** — `_docs/project.md`, `_docs/stack.md`, `PRODUCT.md`. Короткие и могут отставать; при расхождении правы первоисточники.

Правила:
- Изменение объёма v1.0 или списка правил начинается с STRATEGY.md, затем — этот файл.
- Расхождение по объёму между документами ниже STRATEGY.md → прав этот файл; остальные исправляются.
- Новая функция попадает в версию только строкой здесь. Нет строки — функция не запланирована.
- Метки в тексте документов: **[v1.0]**, **[v1.1]**, **[v2.0]**; архитектура исполнения в технических документах помечается «Deferred to v1.1».

## 2. Словарь: что значат слова в v1.0

| Слово | В v1.0 | Не означает в v1.0 |
|---|---|---|
| **Применить / выполнить** | человек вручную вносит изменение в интерфейсе Директа и отмечает «Выполнено вручную»; AdPilot фиксирует исходное состояние и сверяет выполнение по данным Директа (чтение) | запись в кабинет через API, кнопку «Применить» |
| **Решение** | «Принять к выполнению» · «Проверил» · «Позже» · «Не буду» (с причиной) — одним участником с правом decide | одобрение, кворум, уровень риска как условие записи |
| **Автоматизировать** | автоматические только чтение, аудит, сверка, замер и оповещения | автоматические изменения в кабинете — v2.0 |
| **Откатить** | человек вручную возвращает значение в Директе, опираясь на исходное состояние, которое AdPilot зафиксировал при ручном выполнении | механизм отката через API — v1.1 |
| **Предпросмотр** | «что сейчас по снимку · что поставить · где это в Директе» как инструкция для ручного выполнения | предпросмотр «было → станет» для применения через API — v1.1 |
| **AI** | AI-аналитик только для чтения: объясняет рекомендации («Почему AdPilot так считает?») и отвечает на вопросы по данным текущего workspace из `AnalysisContext`, каждый ответ — через валидатор (STRATEGY §6) | изменение рекламы, вызов «Применить», расчёт денег вне структурированного результата, доступ к другому workspace, автономные агенты |
| **Data Health** | постоянный статус-бар: подключения, последняя синхронизация, актуальность и полнота данных; при устаревших или неполных данных рекомендации, которым нужны эти данные, ограничиваются | пункт меню; «зелёный» статус без проверки |

## 3. v1.0 — входит

### 3.1 Продукт

| Что | Где описано |
|---|---|
| Яндекс.Директ (N кабинетов в workspace) + Яндекс.Метрика через OAuth — только чтение данных, не вход | PRD §4 · ARCHITECTURE §2.6–2.8 |
| Снимки данных, ежедневный аудит, свежесть данных и здоровье интеграций | PRD §2, §4 · ARCHITECTURE §4 |
| **TRUTH FIRST:** Truth Layer перед расчётами; `"--"` и отсутствие строки ≠ 0; тип `calculated` в контракте `Value` (FACTUAL · CALCULATED · ESTIMATED · UNAVAILABLE) | STRATEGY §2 · API_CONTRACT §2 |
| **Data Health** и ограничение рекомендаций при устаревших/неполных данных (порог устаревания — ARCHITECTURE §2.6) | STRATEGY §5 · PRD §5 |
| **Ровно три правила:** нулевые конверсии · высокий CPA (target / baseline) · площадки РСЯ без конверсий | STRATEGY §5 · PRD §4 |
| Приоритизация; итог «Расход с признаками неэффективности ≈ N ₽» без двойного учёта | PRD §4 · ECONOMICS |
| Рекомендации с доказательствами и «Почему AdPilot так считает?»; уверенность по правилу; политика безопасности | PRD §2, §5 · AI_GOVERNANCE §2 |
| **AI-аналитик (read-only)** над `AnalysisContext`, с обязательным валидатором | STRATEGY §6 · AI_GOVERNANCE §3 |
| Решение человека и ручная фиксация действия; причины отклонения | PRD §5 · API_CONTRACT §3–4 |
| Фиксация исходного состояния, сверка ручного выполнения по данным Директа | PRD §5 · API_CONTRACT §3 |
| Замер эффекта через 7 дней, «Сэкономлено ≈» по подтверждённым выполнениям | PRD §1 · ARCHITECTURE §5 |
| Кабинет: **Анализ** (главный экран) · Рекомендации · Эффект · Подключения · Настройки; Data Health — статус-бар | PRD §5 |
| Пользователи: собственник бизнеса, маркетолог/директолог, агентство — одна платформа | STRATEGY §3 |
| Telegram-оповещения без названий клиентов, кампаний, запросов, логинов | PRD §2, §5 · ARCHITECTURE §8 |
| Агентства: организация, клиентские workspace, команда, роли | PRD §5 · API_CONTRACT §10 |
| Бесплатный первый аудит, подписка, честный биллинг | PRD §7 · ARCHITECTURE §7.3 |

Статусы рекомендации v1.0: `new` → `requires_decision` → `accepted` → `applied` (`execution_mode = manual`, сверка `verification_status`) → замер; а также `postponed`, `rejected` и «Проверил» (`applied`, `execution_mode = none`) для `inspect_only`. Подробно — PRD §5.

## 7. Открытые вопросы по объёму

1. **Запуск регистрации по SMS** — HOLD до заключения юриста по ч. 10 ст. 8 149-ФЗ (LEGAL.md, PRD §10 №13); до заключения работает резервный вход через Яндекс ID (STRATEGY §8).
2. **Не названы в решении 2026-10-03:** «Почему цифры отличаются?», утренний дайджест и недельный отчёт в Telegram. Раздел «Аналитика» влит в «Анализ». Если не укладываются в план — первыми переносятся «Почему цифры отличаются?» и недельный отчёт. Подтвердить.
3. ~~Пороги «достаточного объёма данных»~~ — утверждены 2026-10-03 (PRODUCT_SPEC §9.1).
4. **Агентству: сводный обзор всех кабинетов и отчёт для клиента** (ссылка/PDF, позже white-label) — обещаны на лендинге; версия не решена. Рекомендация агентов — v1.0 (без них у агентства нет причины платить).
5. **Основной канал уведомлений** — Telegram замедляется с 10.02.2026 и требует уведомления РКН о трансграничной передаче (LEGAL.md); email через российского провайдера как основной или резервный — решение владельца.
6. **Идеи без версии** (PRD §6): рейтинг здоровья рекламы, AI-контроль подрядчика, настройка порогов готовых правил.
7. **Напоминание о списании без email** (PRD §10 №15): канал для пользователя без email и Telegram не решён.
