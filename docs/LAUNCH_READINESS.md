# Запуск INROU с настоящими аккаунтами

Актуально на 28.10.2026. Код и локальные проверки не заменяют настройку внешних сервисов. У владельца пока нет сервера, домена, подтверждённого отправителя и одобренного API-приложения. Поэтому реальный пилот ещё не открыт.

## Что сделать владельцу по порядку

1. **Сразу подать заявку на API Директа.** Зарегистрировать приложение INROU на [Яндекс OAuth](https://oauth.yandex.ru/). Выбрать доступ к API, права `direct:api` и `metrika:read`. По актуальной инструкции Яндекса добавить также `passport:business`, если требуется авторизация от организации. Затем в Директе → Настройки API → Мои заявки подать заявку с ClientID. Для страницы настроек разработчику нужна хотя бы одна кампания; оплачивать или запускать рекламу для этого инструкция не требует. Описать чтение статистики, рекомендации и ручное принятие решений. **Создание приложения ещё не даёт доступ к API: требуется одобрение; срок рассмотрения — до 7 дней.** Пользователи INROU не создают свои приложения. [Инструкция Яндекса](https://yandex.ru/dev/direct/doc/ru/concepts/register).
2. **Выбрать сервер в РФ.** Для 2–3 тестировщиков начальный ориентир — Linux, 2 vCPU, 4 ГБ RAM, 25+ ГБ SSD; это оценка для небольшого пилота со сборкой, а не результат нагрузочного теста. Нужен VPS с Docker, а не хостинг статических страниц. У [SpaceWeb есть тест VPS на 3 дня](https://help.sweb.ru/testovyj-period-na-vds_1039.html), включая день заказа, после подтверждения телефона. На тесте закрыт SMTP — используем почтовый HTTPS API. Для полноценного замера через 7 дней понадобится продлить сервер: трёх дней недостаточно. Постоянно бесплатный сервер в РФ этим планом не обещается.
3. **Зарегистрировать домен или использовать уже контролируемый HTTPS-поддомен.** Пример адреса: `app.ВАШ-ДОМЕН.ru`, почтовый отправитель `noreply@ВАШ-ДОМЕН.ru`. Не считать, что пример свободен. В DNS указать A-запись на IP сервера. HTTPS и обратный прокси настроить через существующий `deploy/Caddyfile`; сертификат выпускается после правильной DNS-настройки. Доступ к DNS нужен и для подтверждения почты.
4. **Настроить почту.** Зарегистрироваться в [Unisender Go](https://go.unisender.ru/), добавить домен и адрес отправителя, внести выданные сервисом SPF/DKIM-записи, дождаться подтверждения. Создать API-ключ и сохранить в приватном окружении сервера. Использовать транзакционные письма подтверждения и восстановления, проверить доставку на почту будущих тестировщиков. Проверить действующий тариф, лимиты и тарификацию сверх лимита в кабинете провайдера; бесплатность навсегда не предполагается.
5. **Подготовить реальные документы и контакты.** Указать оператора, действующие реквизиты и контакт поддержки; согласовать оферту, согласие на обработку данных, политику, cookies и условия пилота. Сейчас в реестре есть шаблоны: их нельзя объявить утверждёнными. Новый текст получает новую версию, старые редакции сохраняются. Разработчик публикует тексты и точные утверждённые SHA256. Сайт автоматически получает текущие версии; согласие ссылается на ту же редакцию, которую отправляет форма.
6. **Передать разработчику доступ к размещению и статус готовности.** Нужны адрес сервера, домен, подтверждённый отправитель и статус заявки Яндекса. Client secret, ключ почты, ключи шифрования и пароли вводятся в секреты хостинга/закрытый `.env`, не в GitHub и не в сообщения. Отдельное приложение Яндекс ID для выбранного входа по email не требуется.

## Что делает разработчик после получения этих входов

7. Развернуть последнюю проверенную версию из [репозитория inrou](https://github.com/woorldmun-commits/inrou). Не переносить старую dirty-копию поверх очищенного проекта. PostgreSQL, Next.js и API не открывать напрямую; снаружи — HTTPS-прокси. Использовать отдельные роли БД, стабильные сохранённые ключи и подписанный адрес посетителя из перезаписываемого ingress-заголовка. Порядок — [deploy/README.md](../deploy/README.md).
8. Перед сборкой установить **одинаковый** публичный HTTPS origin в `NEXT_PUBLIC_SITE_URL`, `INROU_APP_ORIGIN`, `INROU_EMAIL_ORIGIN`, `API_ALLOWED_ORIGINS`. Compose получает build args из `docker compose --env-file deploy/.env …`; `env_file` внутри сервиса задаёт только runtime. Смена адреса требует пересборки frontend. Для закрытого теста оставить `INROU_STAGING=1` и `INROU_DEMO=0`.
9. Включить email с подтверждённым отправителем: `INROU_EMAIL_ENABLED=1`, `INROU_MAIL_PROVIDER=unisender`, приватные `INROU_MAIL_API_KEY`, `INROU_AUTH_HMAC_KEY`, `INROU_SMTP_FROM`. Настроить отдельный почтовый worker и `WORKER_QUEUE_DATABASE_URL`; ключ HMAC не менять при наличии неистёкших задач. Опубликовать реальные документы с утверждёнными хэшами.
10. После одобрения Яндекса настроить `YANDEX_API_*`, `YANDEX_API_ENABLED=1`, ключ шифрования токенов. Для нового API-приложения с кодом подтверждения используется `YANDEX_API_REDIRECT_URI=https://oauth.yandex.ru/verification_code`; существующий одобренный web callback не менять без причины. INROU поддерживает оба сценария. Указать scopes, реально выданные приложению; работа от имени организации требует отдельной проверки прав. Яндекс технически выдаёт более широкое право API, но INROU использует запросы чтения.
11. Включить загрузку и аудит: `WORKER_ENABLED=1`, отдельные DSN рабочих ролей, `RELEASE_COMMIT_SHA`, `RELEASE_BUILD_ID`. Для страницы разбора подключённых снимков нужны `INROU_INTELLIGENCE_ENABLED=1` и, только после согласованного допуска обработки реальных данных, `INROU_INTELLIGENCE_REAL_DATA_APPROVED=1`. `DIRECT_PLACEMENTS_REPORT` оставить выключенным до отдельной приёмки реального отчёта площадок; дополнительные каналы и внешнюю LLM не включать для этого пилота.
12. Для каждого тестировщика создать **свой аккаунт и workspace**, один рекламный кабинет на пространство; добавить разрешённые ID в `PILOT_WORKSPACE_IDS`. Выдать доступ на согласованный срок, например 14 дней через `PILOT_ACCESS_UNTIL`, и обеспечить сервер на весь срок. Обычный trial длится 168 часов: он может закончиться раньше замера через 7 дней после ручного действия. Пилотный допуск не создаёт фиктивную оплату. Не включать общий `PILOT_OPEN_ACCESS` для всех посетителей.
13. Запустить `python deploy/readiness.py` с приватным окружением. Код 0 подтверждает только полноту конфигурации. `launch_approved` остаётся `false`: реальные сценарии ниже требуют ручной приёмки.

## Приёмка перед приглашением 2–3 человек

14. Пройти регистрацию → настоящее письмо → подтверждение → вход → выход → восстановление пароля. Проверить просроченную и повторно использованную ссылку, недоступную почту, ограничения попыток и поддельные IP-заголовки. По email должен открываться собственный кабинет с заметной кнопкой подключения Директа.
15. Каждый участник сам разрешает доступ в Яндексе. Проверить логин кабинета, счётчик и цели, затем первую и повторную синхронизации. Клиент не передаёт оператору пароль или OAuth-токен. Новые live-снимки принимаются только после подтверждения валюты RUB у всех кампаний; неизвестная/другая валюта останавливает загрузку. Исторические снимки этим автоматически не проверяются: для пилота нужен новый подтверждённый sync.
16. **Сверить цифры с Яндексом.** Выбрать один аккаунт, одинаковые даты, НДС, цели и модель атрибуции. Сопоставить расход, показы, клики и конверсии кампаний; CPA считать как сумму расхода / сумму сопоставимых конверсий, не среднее CPA строк. Проверить общий итог, дневной ряд и таблицу. Неизвестное значение не превращать в ноль; отсутствие строки без показов не считать потерянным отчётом автоматически. Даты статистики Директа — по Москве, независимо от часового пояса таргетинга. [Документация Campaigns.get](https://yandex.ru/dev/direct/doc/ru/campaigns/get), [справка Директа](https://yandex.ru/support/direct/ru/troubleshooting/shows).
17. Проверить изоляцию: пользователь A не видит workspace, API-ответы и рекомендации B; viewer не меняет настройки. Проверить отзыв сессии и токена, ошибку источника, восстановление очереди и явный статус устаревших данных. Сделать закрытый `pg_dump` и восстановить на отдельной БД, проверить RLS, доступность ключей и retention. Настроить контроль health, возраста очереди, свежести снимков, ошибок почты и срока сервера/резервной копии. Успешный HTTP `/api/health` сам по себе не подтверждает работу очередей.
18. После приёмки отправить 2–3 людям HTTPS-ссылку, дать задачу «подключить кабинет → объяснить одну рекомендацию → проверить основания», собрать затраты времени, ошибки и вопросы. Экономию и причинный эффект до проверенных измерений не заявлять.

## Что остаётся за пределами первого пилота

| Пункт | Текущий статус / следующий шаг |
|---|---|
| Названия кампаний вместо внутренних ID | Нужен проверенный справочник и расширение контракта; текущий поиск — по ID текущего списка |
| Несколько рекламных аккаунтов в workspace | Планировщик обходит их отдельно, ручной sync выбирает первый; пилот ограничить одним аккаунтом, затем добавить явный выбор/обновление всех |
| Отчёт площадок РСЯ | Код существует, live gate закрыт до приёмки реального отчёта |
| Приглашения/изменение ролей | UI показывает права; самостоятельное управление командой ещё не реализовано |
| CRM, коллтрекинг, VK, Авито | Планируются, рабочие API-подключения не заявлены |
| PDF/XLSX, шаблоны/расписание отчётов | Есть недельный TXT; остальные сценарии не реализованы |
| Оплата | Отдельная приёмка провайдера; для бесплатного пилота не нужна |
| Гарантия ROI/превосходство над конкурентами | Нужны реальные сравнительные данные и методика; это не свойство числа субагентов |

## Кто проверяет качество

К 10 существующим IDE-профилям добавлены [Data Contract QA](project-agents/data-contract-qa.md) и [Runtime Reliability](project-agents/runtime-reliability.md). Первый независимо сверяет источник → снимок → расчёт → число/график. Второй проверяет очереди, свежесть, почту, восстановление и эксплуатационные ограничения. QA/frontend отвечает за графики и UX, backend — за формулы, интеграции — за контракты источников, supervisor — за доказательства точной версии.

Это **12 профилей работы разработчиков**, не 12 автономных фоновых AI-агентов. Метрики считает существующий детерминированный код. Новые имена не подключают LLM, провайдеров или мониторинг сами по себе. Статистика подключается к оценке причинного эффекта по мере появления реальных данных.
