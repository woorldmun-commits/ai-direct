# INROU — автоматический цикл Chief Analyst · 30.10.2026

**Текущая реализация:** после штатной синхронизации Яндекс Директа и Метрики `app.worker.runner` создаёт `audit_runs`. На следующем проходе worker помещает новые аудиты в durable `chief_analysis_jobs`, обрабатывает их и сохраняет ограниченные структурированные результаты. Клиент видит историю в AI-разделе. Нет внешнего LLM, AI-бюджета, автоматического применения изменений, доказанного причинного эффекта и фоновой отправки новых email.

## Точный путь

1. Регистрация email/пароль, проверка документов и согласий, trial/оплата, подключение Директа и отдельно Метрики — существующий код; в демонстрационной конфигурации они выключены.
2. Worker `schedule_syncs` и `run_sync` сохраняют неизменяемый sealed snapshot; `run_audit` создаёт audit_run. Создание job выполняется из зафиксированного аудита: при аварии до enqueue следующий `enqueue_recent` восстановит задачу.
3. `chief_analysis_jobs`: одна строка на audit_run; RLS, foreign keys, статус, максимум 4 попытки, lease 3 минуты, экспоненциальный retry, защита от конкурирующих workers через транзакционный row lock и fencing по `attempts`.
4. В момент исполнения worker повторно проверяет доступ клиента и сравнивает snapshot IDs с `audit_run_snapshots`, состав источников и дату периода. Если что-то изменилось, результат `blocked`, а не ретроактивная подмена данных.
5. Программистские расчёты через `calculate_metrics` (Decimal + evidence); CPA пересчитывается, Chief маршрутизирует доступные диагностические роли. Независимая аутентичность/атрибуция и причинность **не доказаны**; Challenger не разрешает применение изменений.
6. Статусы `queued/running/completed/blocked/failed/skipped` доступны через `GET /api/v1/workspaces/ws_<id>/intelligence/chief-history`. Авторизация workspace, API gateway allowlist, максимум десять записей. В AI-кабинете — история и отдельно on-demand результат.
7. При unavailable/partial/stale история сохраняет причины. Данные одного клиента не смешиваются с другим и не уходят внешнему провайдеру LLM.

## Как включать безопасно

По умолчанию новая автоматизация **выключена**. Для production *после* реальной юридической, инфраструктурной и API-проверки оператор запускает:
- `WORKER_ENABLED=1` вместе с отдельным живым `python -m app.worker.runner` с рабочими DSN `WORKER_QUEUE_DATABASE_URL` (роль `app_system`) и `WORKER_DATABASE_URL` (роль `app_token`);
- `INROU_INTELLIGENCE_ENABLED=1`;
- `INROU_INTELLIGENCE_REAL_DATA_APPROVED=1` только после допуска данных, не на демо;
- `INROU_AGENT_AUTOMATION_ENABLED=1` — *новый* отдельный kill switch.

`render.yaml` остаётся демонстрационным, `WORKER_ENABLED=0`, `YANDEX_API_ENABLED=0`, email закрыт. **Не включать** новые флаги в Frankfurt preview или без реального выполнения требований законодательства. Отключение `INROU_AGENT_AUTOMATION_ENABLED` приостанавливает обработку; поставленные задачи не пропадают.

## Гарантии и ограничения

- `completed` означает, что код выполнил структурированную предварительную диагностику, **не** что доказано финансовое улучшение или человек подтвердил рекомендацию.
- Актуальный `campaign_stats.build` использует последнее sealed состояние; если после аудита пришёл другой snapshot, job блокируется и ждёт следующего аудита, вместо подмены evidence.
- История не хранит тексты поисковых запросов, названия кампаний, email, токены или сырые API-ответы. Доступна клиенту только внутри своего workspace.
- Retention: job привязан к audit_run через `ON DELETE CASCADE`; когда аудит удаляется, история исчезает с ним.
- Результат не зависит от сторонних моделей; дорогие/незавершённые агенты Search Intent, Landing CRO, Customer Value возвращают `unavailable`, пока нет разрешённых источников.
- Полный AI с реальным распределением задач, независимой идентичностью reviewer, CRM, поисковыми запросами и уведомлениями требует отдельных интеграций и безопасного операционного выпуска.

## Тестирование и принятие

- `cd backend && python -m pytest tests/test_chief_automation.py tests/test_migrations.py tests/test_specialist_runtime.py -q`
- `cd backend && ruff check . && python -m pytest -q`
- `cd 'designe 1.0' && npm ci && npm run lint && npm run build`
- Включение на тестовом production-like окружении только после подтверждения доступа, двух независимых организаций, настоящих аккаунтов Яндекс OAuth, доставки ошибок, резервного восстановления и полного CI. Проверка отказа при revoke access, cancellation/expired trial, изменившемся snapshot и no data.
- Итоговый продуктовый релиз только после отдельного владельческого и юридического approval.
