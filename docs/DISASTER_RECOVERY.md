# Восстановление после сбоев — v1.0

> Что делаем, если потеряны или повреждены данные, ключи или окружение. Основа — решение D17 (P0, 2026-10-02). Связанные документы: [ARCHITECTURE.md](ARCHITECTURE.md) §2.3 (роли БД), §2.5 (хранение и удаление), §5.1 (outbox), §7.1 (токены), §7.3 (биллинг), §10 (развёртывание), [LEGAL.md](LEGAL.md).
>
> **RPO и RTO ниже — цели, а не измеренные значения.** Фактические значения появляются только из протоколов тестов восстановления (§5).

## 1. Цели

| Показатель | Цель | Чем обеспечивается |
|---|---|---|
| RPO (сколько данных можем потерять) | ≤ 15 минут | PITR Managed PostgreSQL (Yandex Cloud) |
| RTO (сколько сервис недоступен) | ≤ 4 часа | процедура §4, инфраструктура из кода (docker compose, ARCHITECTURE §10) |

Бэкапы Managed PostgreSQL хранятся 7 дней (ARCHITECTURE §2.5). Срок PITR-окна и фактический RPO провайдера — **проверить** в документации Yandex Cloud и подтвердить первым тестом.

## 2. Что где хранится и как восстанавливается

| Компонент | Источник истины | При потере |
|---|---|---|
| PostgreSQL | **да** — единственный | PITR / бэкап (§4) |
| Redis (очереди arq, кэш, счётчики лимитов, дедупликация) | **нет** | пересоздать пустым; задачи восстанавливаются из состояния PostgreSQL и `outbox_events` (§3) |
| Ключ шифрования токенов (Lockbox / переменная окружения) | да, для токенов | резервная копия ключа (§3.2); при потере — §3.2 |
| Код и конфигурация | репозиторий + `releases` | пересобрать по `commit_sha` |
| Логи (Cloud Logging) | нет | не восстанавливаются, срок 30 дней |
| Платежи | платёжный провайдер | сверка по idempotency-ключам (§3.3) |

## 3. Особые случаи

### 3.1 Redis — не источник истины
- Повторяющиеся задачи (синхронизация, аудит, дайджест) запускает cron arq — после старта воркера они снова в расписании.
- Недоставленные события — в `outbox_events` (`delivered_at IS NULL`); воркер доставки забирает их сам (ARCHITECTURE §5.1). Получатели идемпотентны по `id` события.
- Исполнение в Директе: попытка, у которой есть `execution_started`, но нет итога, — **не повторяется вслепую**: воркер перечитывает объект и пишет `succeeded` или `failed` по факту (EXECUTION_SAFETY §6.2). Повтор — только новой попыткой с новым `idempotency_key` и через полный гейт.
- Потерянные счётчики лимитов (SMS-коды, «Спросить AI») обнуляются — допустимо; дневная дедупликация уведомлений может дать повторное сообщение — допустимо.

### 3.2 Ключ шифрования токенов
- Ключ хранится в Lockbox; резервная копия ключа — отдельно от бэкапов БД и с отдельным доступом (где именно — **открытый вопрос** §7). Бэкап БД без ключа не раскрывает токены — это свойство, а не проблема.
- Версии ключа (`TOKEN_ENCRYPTION_KEY_VERSION`, ARCHITECTURE §7.1) резервируются все, пока есть записи, зашифрованные ими.
- **Ключ потерян:** токены неработоспособны. Подключения переводятся в `token_expired` (или отдельный `status_detail` — решается в PR), шифротекст удаляется функцией сброса токена; пользователи переподключают Директ и Метрику. Снимки, выводы, рекомендации и история не затронуты — они не зашифрованы этим ключом. Уведомление пользователям — через обычный канал статуса интеграции.

### 3.3 Биллинг
- После восстановления БД на момент T платежи провайдера после T в нашей БД отсутствуют. Сверка с провайдером по idempotency-ключам (`Idempotency-Key` оформления, отмены, отказа — ARCHITECTURE §7.3) и ID платежа: недостающие платежи и смены статуса подписки дописываются как события.
- До завершения сверки автосписания приостановлены — нельзя списать повторно по подписке, оплату которой мы «забыли».

### 3.4 Удалённые данные не «воскресают»
После восстановления из бэкапа, **до открытия доступа**:
1. повторно применить все `deletion_requests`, завершённые после точки восстановления (журнал — в самой БД; если журнал тоже откатился — **открытый вопрос** §7);
2. запустить ретеншн (тексты запросов старше 60 дней, снимки без ссылок, ПД деактивированных пользователей — ARCHITECTURE §2.5);
3. только после этого — открыть API и запустить воркеры.

Это уже обещано в политике хранения (ARCHITECTURE §2.5, строка «Бэкапы БД») и здесь становится шагом процедуры.

## 4. Порядок действий при восстановлении БД

| # | Шаг | Кто |
|---|---|---|
| 1 | Объявить инцидент, остановить `api` и все воркеры (запись в БД прекращена) | дежурный |
| 2 | Определить точку восстановления (до повреждения) | дежурный + ответственный за данные |
| 3 | Восстановить кластер PITR в **новый** кластер (старый не трогаем до конца разбора) | дежурный |
| 4 | Проверить роли БД и права (`app_rw`, `app_token`, `app_system`, `app_deleter`, `app_migrator`, роли воркеров — ARCHITECTURE §2.3, EXECUTION_SAFETY §9) и членство `app_token`/`app_system` в `app_rw` (роли — на уровне кластера), append-only триггеры, политики RLS (`tenant` для `app_rw`, `system` для `app_system`) | дежурный |
| 5 | Повторно применить удаления и ретеншн (§3.4) | дежурный |
| 6 | Пересоздать Redis пустым | дежурный |
| 7 | Проверить доступ к ключу токенов (§3.2) | ответственный за секреты |
| 8 | Запустить воркеры с приостановленными автосписаниями и исполнением в Директе | дежурный |
| 9 | Сверка биллинга (§3.3); разбор незавершённых попыток исполнения (§3.1) | ответственный за биллинг |
| 10 | Открыть API; включить автосписания и исполнение | ответственный за данные |
| 11 | Протокол: время, точка восстановления, фактические RPO/RTO, что потеряно, что сделано | дежурный |

Нужно ли уведомлять РКН и пользователей (если инцидент — утечка, а не только потеря) — LEGAL.md; DR-процедура этого не решает.

## 5. Тест восстановления

- **Ежемесячно**, в изолированное окружение (без доступа к Директу, Метрике, платёжному провайдеру, SMS- и SMTP-провайдерам — внешние вызовы отключены конфигурацией).
- Шаги §4 с 3 по 7 на реальном бэкапе + проверки: число строк ключевых таблиц, последний снимок, append-only триггеры работают, удаления после точки восстановления применены, токены расшифровываются резервным ключом.
- **Протокол** (в репозитории или хранилище документов — **открытый вопрос**): дата, кто проводил, точка восстановления, фактические RPO и RTO, отклонения от целей, что исправить.
- Изолированное окружение уничтожается после теста — в нём ПД клиентов (152-ФЗ).

## 6. Ответственность

| Роль | Отвечает за |
|---|---|
| Дежурный (на старте — разработчик) | процедура §4, тест §5, протокол |
| Ответственный за данные / ПД | решение о точке восстановления, удаления §3.4, связь с LEGAL.md |
| Ответственный за секреты | резерв ключа токенов, доступ к Lockbox |
| Ответственный за биллинг | сверка §3.3 |

На старте все роли может совмещать один человек; конкретные имена — вне репозитория.

## 7. Открытые вопросы

1. Где хранится резервная копия ключа шифрования токенов и кто имеет к ней доступ.
2. Если повреждение затронуло сам журнал `deletion_requests` — откуда брать список удалений (внешняя копия журнала?).
3. Где хранить протоколы тестов восстановления.
4. Срок PITR-окна Managed PostgreSQL и фактический RPO — **проверить** у провайдера.
5. Восстановление VM (Compute) — образ или пересборка из репозитория; цель RTO 4 часа это допускает, но процедура не описана.
