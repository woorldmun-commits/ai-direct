# INROU — REA (Reverse Engineer Anything) для Codex

**Статус:** подготовлена интеграция MCP на уровне доверенного репозитория; это НЕ подтверждает установку в пользовательском Codex. Реальный вызов инструментов должен быть проверен на машине разработчика. **Не добавлять REA в клиентский backend, runtime и продуктовых AI-агентов.**

## Источники и версия
- Исходный репозиторий: https://github.com/morluto/rea
- Официальная установка: https://github.com/morluto/rea/blob/main/docs/installation.md
- Skill: https://github.com/morluto/rea/blob/main/.agents/skills/reverse-engineer-anything/SKILL.md
- Зафиксированная версия MCP: `rea-agents@6.8.0`; не заменять без проверки зависимостей.
- Требуется Node.js **22.23.4+ в ветке 22**, **24.22.1+ в ветке 24** или **26.12.1+ в ветке 26** и npm. Другие ветки Node не поддерживаются указанной версией REA.

## Подключение
Файл `.codex/config.toml` регистрирует REA MCP для Codex в этом репозитории, если проект отмечен как доверенный. Первое подключение требует доступного `npx`, сети к npm и совместимого Node.js. **Проектный конфиг не устанавливает сам skill.**

На машине с Codex:
1. Проверить `node --version`, `npm --version`, доступность официального npm-пакета.
2. Вне каталога проекта запустить `npx -y rea-agents@6.8.0 setup --client codex --dry-run`. Проверить пути, резервные копии и план изменений.
3. Если необходимо установить matching skill или системную регистрацию, после явного одобрения запустить `npx -y rea-agents@6.8.0 setup --client codex`. Не дублировать слепо глобальную MCP-регистрацию при уже рабочем проектном конфиге.
4. Перезапустить Codex. Проверить `codex mcp list` и `npx -y rea-agents@6.8.0 doctor --client codex --json`. **Только успешный вызов реального MCP-инструмента** подтверждает рабочую интеграцию.
5. Если автозапуск через `npx` не работает на Windows, выполнить официальный setup, который выберет поддерживаемый launcher и путь к runtime; не обходить ограничения безопасности Codex.

## Когда REA полезен
Применять только когда нужен анализ **работающего сайта, собранного JavaScript-бандла, Electron-приложения, поведения без исходников, сравнения браузерных снимков или независимого runtime-evidence**. Для обычного анализа исходного Next.js/Python-репозитория INROU использовать стандартные средства GitHub и существующие project skills.

**Пример 1 — исследование референса:**
`https://codeandchill.store/templates/kerfa`

1. Открыть публичный сайт в контролируемом браузере Chrome/Chromium через CDP. Не обходить авторизацию, платный доступ, защиту и лицензию.
2. Через REA `list_browser_targets`, `inspect_web_page`, при необходимости `capture_web_screenshot` и `observe_web_session` получить DOM, Accessibility, ресурсы, доступные скрипты и наблюдаемые переходы. Наличие API/DOM события отдельно отрефлексировать как evidence, не как достоверное знание оригинальных исходников.
3. Составить evidence-таблицу: компонент; наблюдаемое поведение; сохранённый источник/путь; известные параметры; недоступное/гипотеза.
4. Для INROU создать **собственные** интерфейсные решения: аккуратные стеклянные панели, компактные KPI, графики с выделением значений, анимации переключения, keyboard navigation, reduced motion. Не копировать коммерческий шаблон, дизайн/код/изображения и закрытые ресурсы.

**Пример 2 — проверка собственного собранного веб-приложения:**
- Исходники: `designe 1.0/` (Next.js 16), не путать с готовым JS-бандлом.
- Для статической REA-проверки сначала построить сборку с `npm ci` и `npm run build` из каталога `designe 1.0` в изолированном окружении, затем указывать REA именно существующий сборочный артефакт.
- Для runtime-проверки — только публичное демо или изолированная тестовая среда; никогда не захватывать реальный OAuth, cookie, email, токены Метрики и Директа или клиентские агрегаты.
- Сверять скриншоты с **одним** утверждённым эталоном INROU Midnight Sapphire на desktop/tablet/mobile и в обеих темах. Разницу в плотности, карточках, сетке, текстах, графиках, тенях и анимации фиксировать отдельно.

## Проверки качества
- Ссылки на Evidence, version/hash целей и границы наблюдения для каждого фактического вывода.
- Отдельно: observed / inferred / unknown. Не утверждать абсолютное совпадение 1:1 по одному статичному изображению.
- При работе над интерфейсом задействовать существующий `inrou-frontend` и независимый `inrou-qa`; `inrou-supervisor` выносит итоговый scoped verdict. REA **не** является новым продуктовым AI-агентом.
- Сохранить Evidence First, Human Control, приватность и действующие release gates.
- Любые изменения дизайн-системы — через PR с визуальными тестами, без автодеплоя/слияния.

## Проверка работоспособности в CI
Workflow `.github/workflows/rea-smoke.yml` устанавливает пакет во **временном GitHub runner** и выполняет структурный smoke-test на общедоступных JS-файлах INROU. Это лишь проверка CLI, не доказательство работающего MCP в локальном Codex и не аудит fidelity интерфейса. Диагностика и evidence публикуются как CI-артефакты, если тест прошёл.
