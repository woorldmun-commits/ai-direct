Регрессионные проверки явно запрещают `pool.connection` для отсутствующей/подделанной/просроченной cookie, неверного state, отсутствующего code и ошибки провайдера. Полный набор включает проверки изоляции организаций и workspace под RLS, запрета неподходящих ролей БД, финансового Value/Decimal контракта, CSRF Origin, лимита тела запроса, заголовков на ошибках, отсутствия подробностей внутренних ошибок в ответе, токенов, жизненного цикла и workers.

## OAuth и документы

- Реальные маршруты: POST `/api/v1/auth/yandex/start`, GET `/api/v1/auth/yandex/callback`, POST `/api/v1/auth/logout`.
- Вход отключён по умолчанию. Без настроенного провайдера старт возвращает 503; чужой callback origin/path/небезопасный внешний HTTP URI отвергается настройками.
- State и выбранные версии согласий связаны зашифрованной аутентифицированной HttpOnly flow-cookie с TTL 600 секунд. Подделанная, просроченная, отсутствующая cookie и неверный state не инициируют обмен кода у провайдера.
- Регистрация требует точных утверждённых SHA256 текстов offer и pd_consent. Изменённые/отозванные approvals проверяются повторно на callback. Вход существующего пользователя допускается без нового согласия. Тестовые approvals не являются утверждением документов для эксплуатации.
- GET `/api/v1/legal/documents/{document}?version=...&locale=ru-RU` возвращает точные UTF-8 байты текста через JSON, версию, SHA256 и признак утверждения. Неизвестные документы/версии не раскрывают произвольные файлы.
- Идентичность Yandex проверяется по устойчивому id и client_id, не по одному email. Неправильные типы ответов профиля и токенов отвергаются.
- Новый пользователь получает личную организацию и workspace в транзакции callback. Тесты подтверждают единственный workspace при конкурентном первом входе и полный rollback пользователя/identity/provisioning при ошибке.
- Cookie сессии содержит случайный токен, БД хранит SHA256. При повторном входе прежняя сессия удаляется; logout удаляет текущую. Проверены отозванные и истёкшие сессии.
- API использует только app_rw без SUPERUSER/BYPASSRLS; контекст workspace устанавливается локально для транзакции и проверяется при возврате соединения в пул.

## Обязательные условия до открытия доступа

1. Домен и HTTPS ingress, доверенный callback Yandex, точный API_ALLOWED_ORIGINS, согласованные имена cookie frontend/backend и API_HSTS. API PostgreSQL доступен приложению как app_rw; миграции и административные задачи используют отдельные роли.
2. Реквизиты оператора и утверждённые тексты документов с новой неизменяемой версией. Только после проверки текста оператор задаёт API_SIGNUP_APPROVED_HASHES. Шаблон `.env.example` не содержит рабочих секретов и approvals.
3. Gateway rate limits и ограничения одновременных auth/callback запросов, таймауты и лимиты ingress. Неверная flow-cookie/state уже отвергается до обращения к БД, однако валидная flow-cookie может повторно использоваться вручную до TTL для неуспешных кодов. Обмен с провайдером на валидном flow ещё занимает соединение БД и рабочий поток; ограничения тела/Origin/TTL не заменяют защиту от истощения пула и потоков. Нельзя открывать API напрямую в интернет без этих эксплуатационных ограничений.
4. Реальная проверка входа/выхода с Yandex, отзывов разрешений и восстановления после ошибок. В тестах только транспорт Yandex заменён локальным mock; production provider e2e не выполнен, поскольку конфигурации нет.
5. Административное подключение Direct/Metrika, получение разрешений и загрузка отчётов. Самообслуживание подключения источников через HTTP/UI ещё отсутствует. Пустой кабинет после регистрации не означает неисправность и не должен показывать синтетические показатели.
6. Backup/restore PostgreSQL, управление секретами, мониторинг ошибок и насыщения пула, безопасные журналы без OAuth code/query/cookie/token, процедуры инцидентов и отзыва доступа.

Внешнее сканирование, нагрузочная/DDoS проверка, аудит реального ingress/TLS, полный secrets scan Git-истории и проверка production инфраструктуры в этой работе не выполнялись. Отчёт не является гарантией отсутствия уязвимостей. Зависимости проверяются отдельными итоговыми артефактами родительского аудита; результаты такого сканирования здесь не переобъявляются как собственный запуск.

На этой стадии изменены только backend OAuth callback и его регрессионные тесты, а также этот отчёт. Проверка не затронула frontend-серверы и интеграционную fixture другого агента.
