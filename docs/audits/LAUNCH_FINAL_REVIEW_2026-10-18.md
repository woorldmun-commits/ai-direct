## Проверенные границы

- `backend/app/api/auth.py:78`: callback сначала проверяет наличие и размер flow-cookie, срок Fernet, state и утверждение документов. До успешной проверки соединение из пула не запрашивается. `request_connection` оборачивает `sign_in`, создание организации/пространства и отзыв предыдущей сессии одной внешней транзакцией; вложенная транзакция `sign_in` не фиксирует внешний запрос. Исключение проходит через выход из контекстного менеджера до обработки в callback. Cookie успешной сессии устанавливается после завершения этого блока.
- `backend/app/api/deps.py`: actor определяется по хэшу случайного session-token с проверкой срока, отзыва и активности пользователя. Доступ к workspace проходит через членство и RLS-контекст. Новая страница не вводит альтернативный client-side actor или обход этих проверок.
- `frontend/lib/auth-proxy.ts`: фиксированный набор путей и методов, проверка Origin для POST, ограниченные тело/время чтения, выбранные session/flow cookies, отсутствие произвольного upstream URL, отказ от внешнего redirect. Callback query имеет ограничение длины и запрет дубликатов. Upstream ошибки не раскрывают клиенту служебные детали.
- `frontend/lib/api-origin.ts` и `frontend/lib/pilot.ts`: адрес API задаётся серверной конфигурацией; HTTP допускается только для loopback. В кабинет передаётся только валидный session-cookie. Запросы не кэшируются, redirects API запрещены, JSON ограничен по размеру и проверяется контрактом. Неполученные показатели не подменяются fixture-данными.
- `backend/app/api/legal.py`, `backend/app/legal/documents.py`, `frontend/lib/legal-document.ts`, `/login`, `/legal/[slug]`: точный текст поступает из реестра, из которого вычисляется SHA256 принятия. Frontend проверяет идентификатор, редакцию, язык, тип approved и хэш точного UTF-8 текста. До утверждения обоих обязательных документов регистрационные согласия не показываются. Callback повторно проверяет approvals. Принятие `{}` оставляет путь входа существующего пользователя, но не создаёт нового пользователя. Реестр требует неизменности опубликованной версии; изменение текста требует новой редакции.
- `frontend/components/reference/landing.tsx` и `hero.tsx`: основные обещания соответствуют текущему кабинету чтения — расходы, рекомендации, источники и ограничения. Подключение и загрузка данных описаны как настройка администратором. Схемы интерфейса не выдаются за живые показатели. Ограничение полного паспорта рекомендации явно указано. Главная и metadata не обещают готовый самостоятельный onboarding, CPA-dashboard или автоматические изменения рекламы.
- `/demo` layout, `/demo/ai`, `/prisma-preview` и auth catch-all проверены по исходникам: прежние публичные прототипы заменены переходами; auth catch-all делегирует проверяющему BFF.

Полный backend suite, реальные HTTP-проверки с изолированной PostgreSQL, production build, браузерные проверки и HTTP headers выполняются другими участниками. Их результаты не представлены здесь как независимо повторённые этим ревьюером. Build и серверы в рамках этого ревью не запускались.

## Границы допуска

Владелец подтвердил отсутствие домена, хостинга, реквизитов оператора, настроенного Яндекс OAuth и production-БД. Эти условия нельзя заменить кодом или тестовыми approvals. До запуска нужны собственный HTTPS origin, согласованная серверная конфигурация, реальный provider callback, утверждённые неизменяемые юридические тексты, миграции/ограниченная роль БД и проверенный административный процесс подключения/синхронизации источников.

Внешнее ограничение частоты/параллельности auth-запросов остаётся условием публичного допуска: lazy DB acquisition защищает от заведомо невалидного callback, но не является полноценной защитой публичного ingress от злоупотреблений. В этом ревью не проводились внешняя атака, DDoS, проверка боевого OAuth/синхронизации/резервного восстановления или полная проверка секретов истории Git. Реальные рекламные изменения и платежи не выполнялись.
