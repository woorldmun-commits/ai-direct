# Rekvero: итог проверки и подготовка запуска, 18 октября 2026

**Публичный запуск: NO-GO.** Код и локальный интерфейс доработаны и проверены. Владелец подтвердил отсутствие домена, хостинга, реквизитов оператора, Yandex OAuth и production PostgreSQL. Они не заменялись фиктивными настройками. Локальный просмотр: http://127.0.0.1:3110/.

## Что изменено

- Публичные демо-экраны закрыты переходом в настоящий `/workspace`; signup ведёт к входу, прототип — на главную. Синтетическая статистика не используется как резервный источник данных.
- Первый экран отвечает: Rekvero для директологов и агентств; расходы, рекомендации и свежесть данных; следующий шаг — вход в кабинет. Убраны обещания отсутствующих CPA, конверсий, самообслуживания подключения и выполнения рекламных изменений.
- Рабочий кабинет получает данные сервером из FastAPI, проверяет контракты и показывает отсутствие данных отдельно от нуля. Права проверяются через серверную сессию, членство и PostgreSQL RLS.
- Реализованы старт/возврат Yandex OAuth и выход с отзывом сессии, ограниченный same-origin proxy, HttpOnly cookies, проверка state/срока flow, ограничение размеров и времени запросов. Некорректный callback отвергается до получения соединения БД.
- Регистрация закрыта до публикации точных утверждённых текстов. Frontend сверяет SHA256 полученного документа; backend проверяет утверждение повторно при callback. Реквизиты и юридические утверждения не придуманы.
- Canonical, robots и sitemap используют `NEXT_PUBLIC_SITE_URL`; неподтверждённый чужой домен убран. В `.env.example` добавлены настройки без секретов.
- Выровнены desktop/mobile сетка, типографика, отступы и тени; предусмотрено уменьшение движения. Исправлены lint и измерение ширины вкладок через ResizeObserver.
- Старый `/demo/ai` переведён на динамический redirect: проверка обнаружила, что конфигурационный redirect обходил общие security headers. Повторная проверка проходит без ослабления требований.

## Последовательность допуска к запуску

1. Выбрать принадлежащий владельцу домен и хостинг, настроить HTTPS. До сборки задать реальный `NEXT_PUBLIC_SITE_URL`; `REKVERO_API_URL` — серверный адрес API, HTTPS вне loopback. Имена session cookie должны совпадать.
2. Развернуть PostgreSQL и миграции, предоставить API только роль `app_rw` без SUPERUSER/BYPASSRLS. Отдельно проверить backup/restore и хранение секретов вне Git/client bundle. Шаблон: `backend/.env.example`.
3. Создать Yandex ID приложение, зарегистрировать точный frontend callback `/api/auth/yandex/callback`, задать `YANDEX_LOGIN_*`, точный `API_ALLOWED_ORIGINS` и secure/HSTS. До этого вход намеренно недоступен.
4. Внести реальные данные оператора и утверждённые неизменяемые версии документов. Проверить отображаемый полный текст и SHA256; только затем задавать `API_SIGNUP_APPROVED_HASHES`. Нельзя утверждать bundled drafts одним копированием хэшей.
5. Настроить ingress rate/concurrency limits для auth/callback, лимиты тела, таймауты и наблюдаемость пула/ошибок. Валидный flow с неверным кодом всё ещё может потреблять provider/DB ресурсы; прямое открытие API без gateway защиты не допущено. Не записывать cookies, OAuth codes и tokens в журналы.
6. Администратору подключить реальные разрешённые Direct/Metrika источники и загрузку отчётов. HTTP/UI самостоятельного подключения пока нет. Кабинет только для чтения: полный паспорт рекомендации, workflow решений/исполнения, биллинг и рекламные изменения не представлены как работающие функции.
7. На целевом окружении повторить вход/выход, отзыв разрешений, создание первого workspace, изоляцию клиентов, загрузку источников, headers, browser и backup/restore. Сверить результат с реальным provider transport, который в локальных OAuth тестах заменён mock.

Нет гарантии отсутствия всех уязвимостей; локальный аудит не является аттестацией инфраструктуры.
