# Исправления INROU по аудиту и присланному файлу

Дата: 28.10.2026, Москва. Изменения в основной рабочей папке. Root — единственный писатель приложения; независимый Code Reviewer проверяет результат без правок. Существовавшие изменения сохранены. Коммит, публикация, реальные письма, платежи и рекламные операции в этом проходе не выполнялись.

## Исправлено в коде

### 1. Восстановление непустой базы

Новая миграция `0015_restore_value_helpers` фиксирует search_path всей цепочки четырёх Value helpers. Выпущенные миграции не переписывались. `schema.sql` воспроизводит тот же результат.

Регрессионные тесты проверяют валидные/невалидные значения при пустом caller search_path, затем создают непустую цепочку finding → explanation → recommendation, делают pg_dump и восстанавливают её в другую БД. После восстановления проверяются строки и отсутствие доступа у app_rw без workspace context. Это локальная репетиция с синтетическими данными; восстановление действующего хостинга остаётся отдельным этапом.

### 2. Привязка Метрики к конкретному рекламному аккаунту

`0016_account_metrika_binding` добавляет сохранённый counter и признак подтверждённой настройки. Явное решение «без счётчика» отличается от старой неподтверждённой конфигурации. Первичная, ручная и ежедневная синхронизации берут настройку аккаунта. Воркер получает отдельный токен соответствующего Metrika connection.

Старые подключения требуют повторного подтверждения через подключение; неправильные исторические scheduled rows не используются для угадывания привязки. Поставленные раньше задания с устаревшей конфигурацией пропускаются до внешнего запроса; UI сообщает о необходимости переподключения. Связь защищена от ссылки на чужой workspace. Отложенный FK позволяет штатному удалению всего пространства завершить удаление зависимых сущностей в одной транзакции.

Исторические снимки и рекомендации не переписываются. Если неверные привязки уже использовались на настоящих данных, оператору нужно отдельно определить затронутые снимки и повторить сбор/анализ; существующая история сама не превращается в корректную.

### 3. Семь дней бесплатно без карты

По дополнительному указанию владельца реализован trial: **168 часов с успешного подтверждения email либо создания нового аккаунта Яндекс ID**, один раз на пользователя и одно регистрационное пространство. Даты назначает PostgreSQL; клиент не передаёт срок. Регистрация и выдача доступа атомарны.

Приватный журнал доступен приложению только через функции. Повторный вход, reset, повтор вызова и новые workspace срок не продлевают. Удаление trial-workspace при сохранённой учётной записи не позволяет выдать второй trial. При полном удалении пользователя журнал удаляется вместе с ним; защита от создания новых идентичностей не заявляется.

Общий worker guard, API подписки, Direct и новые Intelligence расчёты используют одно состояние доступа. Начало включительно, конец исключительно; будущий период не даёт доступ. После истечения новые расчёты и sync закрыты, история доступна по правам; чтение уже сохранённого идемпотентного результата не создаёт новый анализ. Пилот оператора и оплаченная подписка сохраняются отдельно, trial не обозначается оплатой. Без карты и автосписаний, лимит trial — один рекламный аккаунт.

В интерфейсе есть основание доступа, даты и состояние окончания. Регистрация на публичном сервере от этого автоматически не включалась: требуются почта, документы и внешняя приёмка. Публичный текст указывает, что семь дней начнут предоставляться после открытия регистрации.

### 4. Отсутствующие конверсии

Direct `--` больше не приравнивается к доказанному нулю. Если неизвестна хотя бы одна запрошенная цель, их сумма неизвестна; числовое `0` остаётся нулём. Расходы и другие известные поля сохраняются.

В high CPA проверяются неизвестные значения оцениваемого окна и baseline. Правила нулевых конверсий/площадок не строят исторический CPA из неполных конверсий. Существующее безопасное поведение при пропущенных днях/досчёте сохранено. SQL-агрегаты статистики уже не складывают NULL как известный ноль.

Числовые пороги правил не менялись. Регрессии отдельно различают отсутствие данных, явный ноль и отсутствие строки дня без активности. Синтетические fixtures, подразумевавшие известный ноль, теперь передают явный `0`; tests с `--` проверяют неизвестность.

Исторические снимки, где старый parser уже сохранил `--` как 0, автоматически не исправляются: исходный смысл восстановить из одного нуля нельзя. Перед реальным запуском нужен новый sync; перенос правил на старые snapshots сам не восстанавливает утраченную семантику.

### 5. Обзор с временными рядами

Постоянный NoSeries на обзоре заменён существующим LiveStats в компактном режиме. Сохранены workspace/account/period filters, честные пропуски, сведения об источнике и качестве. На обзоре не дублируется вся таблица анализа и не появляется второй h1. Общая аналитическая страница продолжает использовать тот же компонент.

### 6. Разбор реальных сохранённых снимков

Добавлен read-only `intelligence/snapshot-analysis`. Он использует существующую агрегацию: один последний закрытый снимок каждого выбранного/доступного аккаунта, общий проверяемый период, сопоставимость определения конверсии и отсутствие двойного счёта. Это чтение сохранённой БД, не новый вызов Яндекса.

Расчёт выполняется теми же ограниченными аналитическими инструментами и Decimal-контрактами. В результат входят ссылки на snapshot IDs, период, качество, подтверждённый бизнес-профиль и ограничения. Неизвестные продажи/выручка/CAC/прибыль не достраиваются. Partial и stale не повышаются до complete.

Новый раздел AI-аналитика показывает расчёт по снимкам, профиль и ссылки на рекомендации последнего аудита. Различие периодов явно отмечено. Сокращённые числовые значения помечены `≈`; исходная точная Decimal строка остаётся в ответе сервера и title.

Время результата фиксируется после чтения источников: закрытие нового снимка во время запроса не нарушает проверку fetched_at ≤ as_of. Этот сценарий покрыт отдельной регрессией.

Доступ закрыт без feature flag, допуска real data, прав workspace и действующего entitlement. Внешняя LLM и выполнение рекламы выключены. Этот мост не является непрерывным автономным AI-директором, обученной памятью клиента или доказанной моделью причин.

### 7. Тарифные названия и актуальный канон

Кабинет показывает названия «Контроль / Бизнес / Агентство», согласованные с backend catalog, не меняя сохранённые plan codes и цены существовавших периодов. Публичные старшие цены не утверждались этим проходом, платёжный провайдер не включался. Обновлён `docs/COMMERCIAL_STATUS.md` о реализованном trial и границах допуска.

## Внешние условия, которые код не может подставить за владельца

1. Утверждённое размещение реальных данных и документы/реквизиты оператора, основной домен и канал поддержки. По текущим требованиям проекта Frankfurt demo не автоматически становится средой клиентских ПД.
2. Подтверждённый sender/domain и аккаунт Unisender Go; API key вводится в hosting secrets. Дальше настоящие verify/login/reset и проверка mail worker/ingress, без обхода gates.
3. Разрешённое приложение Direct/Метрики и тестовые аккаунты; read-only OAuth, выбор целей, первый/повторный sync, сопоставление со source и два изолированных пользователя в облаке.
4. Устойчивая среда, backup/restore и наблюдаемость worker/retention/mail. Render free web засыпает; текущая бесплатная БД истекает 19.11.2026 в 15:56 МСК. Платные ресурсы не создавались, ACL БД до проверки внутреннего пути не менялся.
5. Платежи и финальные коммерческие условия — отдельная приёмка. Trial не требует включать реальные оплаты. Нельзя объявлять ежедневные письма, платежи, причинную экономию или весь AI-директор готовыми по локальным tests.

## Как тестировать дальше

Демо на https://inrou-pilot.onrender.com/demo/overview остаётся публичной опубликованной версией; новые локальные исправления туда ещё не выкладывались. Для UX-тестирования можно пользоваться ранее подготовленной инструкцией `docs/launch-audit-2026-10-28/TESTER_GUIDE.md`.

Первый реальный пилот после внешней приёмки: два сопровождаемых участника, затем расширение. Проверять время до первого результата, пригодность сигналов, причины отклонений, возврат и минуты помощи. Регистрация и техническая активация не равны доказанной пользе и экономике.
