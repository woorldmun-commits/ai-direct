# Проверка пользы inrou / Rekvero на клиентах

Статус: план исследования, а не результаты пилота. Интервью, оплаты и экономия этим документом не подтверждаются.

## Участники и границы

Стартовая гипотеза: специалисты и небольшие агентства с несколькими проектами в Яндекс Директе. Представление для владельца — краткая сводка того же проекта. Это выбор для проверки, а не доказанный лучший сегмент.

Предлагаемый набор: 8–12 компаний, 4–6 недель; срок наблюдения продлить для длинных продаж. Подключение источников только самим участником. Никаких автоматических изменений рекламы. Реальные платежи сейчас отключены по решению владельца продукта. Отчёт участник читает на сайте в «Отчётах»; внешняя рассылка не требуется.

## Интервью до подключения

1. Показать последний случай неожиданного расхода: как обнаружили, сколько заняла проверка, что сделали.
2. Показать последний отчёт клиенту и спорную рекомендацию; определить, какая работа повторяется каждую неделю.
3. Уточнить используемые платные и бесплатные инструменты, число проектов, кто принимает решения.
4. Для лидогенерации согласовать определение квалифицированной заявки, статусы, полный набор аккаунтов и период привлечения.
5. Зафиксировать длительность той же задачи в привычном процессе. Не заменять это вопросом «нравится ли AI».

## Карточка наблюдения

На каждого участника: внутренний ID, модель бизнеса, роль, число проектов, существующие инструменты, текущий процесс, время проверки до, время подключения, ожидание пригодных данных, первый полезный результат, причина возврата на следующей неделе. Контакты хранить отдельно от исследовательской таблицы и не отправлять модели.

На каждый разобранный сигнал: recommendation_id/version_id, период и источник; подтверждён / опровергнут / уже известен / неактуален / недостаточно данных; основание оценки; решение; время проверки; статус повторного замера. Отклонение само по себе не является ложной тревогой.

CSV-эксперимент: участник самостоятельно готовит UUID, даты и статусы; фиксируются ошибки предпросмотра, необходимость помощи, повторный импорт и понятность qCPL. Текущая формула использует расход аккаунтов импортированной когорты, не доказывает атрибуцию каждого лида. lost/refunded входят в квалифицированные как ранее прошедшие квалификацию; для оплаченных заказов нужна другая метрика.

## Критерии до начала пилота

После исходных замеров владелец задаёт минимально полезное сокращение времени, допустимую долю бесполезных сигналов, требуемое покрытие данных и критерий повторного использования. Записать числитель, знаменатель, исключения и срок. Не подбирать пороги после просмотра результатов и не выдавать их за отраслевые нормы.

Измерять подключение, время до полезного вывода, полезность сигналов, время сопоставимой задачи, повторную полезную проверку, обращения в поддержку и отказы. Результат «значимых проблем в проверенной области нет» также может быть полезным.

Покупку и продление оценивать только после включения настоящей оплаты; обещание заплатить записывать как намерение. Сейчас это измерение недоступно.

## Решения после наблюдения

- Продолжать основную функцию, если участник повторно использует её для подтверждённой полезной работы.
- Исправлять качество сигналов и понятность данных прежде расширения числа правил.
- Выбирать один CRM-коннектор по наблюдаемым данным участников, необходимости обновлений и доступу к API. Не назначать amoCRM/Битрикс24 по известности.
- Новые площадки, автоматическое управление рекламой и финансовые обещания — отдельные решения после проверки основного сценария.

Пилот ещё не проведён. Публичные клиентские кейсы добавлять только по согласованным и проверенным материалам.
