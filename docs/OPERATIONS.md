# Эксплуатация и включение

Этот документ описывает готовые команды и оставшиеся внешние проверки. Он не подтверждает их выполнение в production.

1. Применить новые миграции штатной командой проекта; новая версия `0020_worker_health_product_mail` аддитивна. Проверить журнал и schema replay. Старые миграции/их хеши не менять.
2. Direct worker продолжает использовать app_token + app_system. Его основной поток записывает progress перед единицами работы и после завершения. API `/health` остается liveness БД/API.
3. Отдельная проверка с app_system через `WORKER_QUEUE_DATABASE_URL`:

```sh
cd backend
python -m app.worker.progress --worker sync --max-age 300 --max-queue-age 900
```

JSON не содержит клиентских ID/имен/DSN. Exit 0 — в пределах заданных критериев; exit 2 — отсутствующий/устаревший progress, отсутствие успешной работы после начального окна, ошибка или возраст очереди. Порог — операторская настройка под реальные длительности, не обещанный SLA. Вызывать внешним монитором; его размещение и получателя тревоги нужно реально настроить. Команда сама не отправляет сообщений.

4. Продуктовые письма отделены от verify/reset. При готовой почте включить `INROU_PRODUCT_EMAIL_ENABLED=1`; `deploy/serve.py` запустит отдельный `app.worker.product_mail_runner`. При раздельном deployment запустить этот модуль отдельно. Ему не передаются ключи Директа или оплаты.
5. Пользователь самостоятельно включает сервисные письма в настройках каждого пространства. По умолчанию opt-in отсутствует. Нужен подтвержденный email; текущий доступ проверяется при постановке и перед отправкой. Старые события до opt-in не рассылаются.
6. Монитор с включенными письмами:

```sh
python -m app.worker.progress --worker sync --worker product_mail --max-age 300 --max-queue-age 900
```

Обработка единицы/прохода не означает доставку в inbox. После SMTP/HTTP подтверждения задача помечается sent, но внешняя доставляемость проверяется отдельно. Неопределенный сетевой результат может дать повтор: доставка at-least-once. Message-ID не обеспечивает exactly-once. После десяти неудачных попыток требуется разбор оператором; не сбрасывать попытки автоматически без причины. Старые Telegram-задачи не отправляются.

Текущий канал сообщает о новых рекомендациях, без клиентских названий, кампаний и денежных сумм. Это не ежедневный/недельный дайджест. Недельный TXT формируется по запросу в кабинете.

7. При подтвержденной бизнес-политике синхронизация запрашивает 37 + max(3, delay) дней для задержек до 90 дней, максимум 127. Директ поддерживает CUSTOM_DATE; [официальный контракт](https://yandex.ru/dev/direct/doc/en/period). Ресурсные лимиты ответов/источника сохраняются. При большей задержке либо недостаточной истории аудит воздерживается от экономической рекомендации. Проверить объем, время запросов и правила хранения на пилоте до обещания поддержки всех длинных циклов.

Внешняя приемка: две реальные организации с разрешенным доступом, ingress, verify/reset, read-only OAuth/sync, расширенное окно, opt-in/отзыв доступа/письмо, sandbox платеж/сверка, восстановление managed backup, Linux image и hosted CI. Подтвердить фактические результаты, точную версию и оператора. Юридические документы утверждает владелец с профильным специалистом; флаги не заменяют утверждение.
