## 1. Детерминированные компоненты и AI

В AdPilot нет «агентов», которые сами решают и действуют. Есть детерминированные компоненты, которые считают и решают, и два AI-компонента, которые объясняют. Слово «агент» в документах и интерфейсе для них не используем (Agent Registry — **[v1.1]**).

| Компонент | Тип | Что делает | Где | Может менять рекламу |
|---|---|---|---|---|
| Data | детерминированный | синхронизация, allowlist, санитизация, снимки | `sources/`, `sync/` | нет |
| Audit | детерминированный | правила, выводы, суммы, итог без двойного счёта | `rules/`, `audit/` (вкл. `audit/exposure.py`) | нет |
| Safety | детерминированный | `safety_policy`, `risk_policy`, реестр возможностей, гейт, кворум | `audit/policy.py`, `execution/` | только `execution/` после одобрения человека |
| Measurement | детерминированный | замер «Сэкономлено ≈» | `audit/measurement.py`, `worker/measure.py` | нет |
| Explain | **AI** | текст объяснения вывода | `ai/explain.py` | нет |
| Assistant («Спросить AI») | **AI** | ответ на вопрос по данным workspace, только чтение | `ai/ask.py` | нет |
| Root Cause Engine | AI + код | поиск причин изменений | — | **[v1.1]** |

Правило: числа, уровни, риск, суммы и решение «есть ли проблема» — только детерминированные компоненты. AI получает их результат и превращает в текст. Если AI недоступен или ответ не прошёл проверку — продукт работает на шаблонах.

## 2. Утверждения → доказательства (D11)

### 2.1 Контекст из фактов с ID
Контекст собирает бэкенд, не модель. Каждый факт имеет ID в пределах запроса (`e1`, `e2`, …), тип и значения (`Value`):

```json
{"facts": [
  {"id": "e1", "kind": "finding", "object": "campaign_A", "rule": "high_cpa_target@1",
   "values": {"actual_cpa": "4820.00", "target_cpa": "3000.00", "conversions": "19"}},
  {"id": "e2", "kind": "policy_reason", "object": "campaign_A", "reason": "data_partial"},
  {"id": "e3", "kind": "metric_change", "object": "campaign_A", "metric": "cpa", "from": "3580.00", "to": "4820.00"}
]}
```
Значения в примере иллюстративные. Перечень типов фактов — в коде; причинные типы — `finding`, `policy_reason`, `metric_change`.

### 2.2 Ответ модели — структура
```json
{"summary": "…", "claims": [{"text": "CPA кампании A выше целевого: 4 820 ₽ против 3 000 ₽", "evidence_ids": ["e1"]}]}
```

### 2.3 Валидатор (`ai/validate.py`)

| # | Проверка | Не прошла → |
|---|---|---|
| 1 | ответ разбирается в схему `{summary, claims[]}` | шаблон |
| 2 | у утверждения ≥ 1 `evidence_id`, и все они существуют в контексте | утверждение отбрасывается |
| 3 | каждое число утверждения есть **в процитированных фактах** (а не где-то в контексте) | утверждение отбрасывается |
| 4 | причинное утверждение («из-за», «потому что», …) ссылается хотя бы на один факт `finding` / `policy_reason` / `metric_change` | утверждение отбрасывается |
| 5 | в тексте нет ID Яндекса и чисел, похожих на них (§3) | утверждение отбрасывается |
| 6 | отброшено утверждение, на котором держится `summary`, или не осталось ни одного | весь ответ → шаблон, собранный кодом |

- Это заменяет и усиливает прежнюю «проверку чисел» (ARCHITECTURE §6): раньше число могло быть где угодно во входе, теперь — в фактах, на которые ссылается само утверждение.
- Отклонённый ответ не хранится; в лог — факт отклонения и номер проверки, без текста (метрики §5).
- Нормализация чисел при сравнении (пробелы-разделители, «₽», «%», запятая/точка, округление) — в коде валидатора с тестами; правило округления — **открытый вопрос** §6.
- Как `summary` связан с утверждениями (ссылается ли он сам на `evidence_ids` или считается производным от claims) — **открытый вопрос** §6.

### 2.4 Непрозрачные ссылки
- В LLM не уходят ID Яндекса (кампаний, групп, площадок, запросов) и логины. Объекты передаются непрозрачными ссылками **на один запрос**: `campaign_A`, `object_3`.
- Таблица соответствия живёт только на сервере в рамках запроса и не сохраняется; обратная подстановка (ссылка → название/ID для показа пользователю) — **после** валидации.
- Ссылки не стабильны между запросами: `campaign_A` в двух ответах — не обязательно одна кампания. Это намеренно: по ответам модели нельзя собрать профиль клиента.
- Как и раньше: названия кампаний и тексты поисковых запросов не уходят никогда (ARCHITECTURE §2.4).

## 3. «Спросить AI» — только чтение (D11)

| Можно | Нельзя |
|---|---|
| объяснить рекомендации, доказательства, замеры, агрегаты аналитики за период | вызывать инструменты записи (их у модели нет) |
| сослаться на существующую рекомендацию | создать, одобрить, применить, отклонить рекомендацию |
| ответить «Недостаточно данных» и что подключить | придумать число, которого нет в фактах |

- Просьба «снизь ставку» → ответ со ссылкой на существующую рекомендацию или «такой рекомендации нет»; исполнение — только обычным потоком рекомендации (EXECUTION_SAFETY.md §1).
- Создание Action Request из чата — **[v1.1]**.
- Хранение: история вопросов и ответов не хранится как пользовательские данные; только технические метаданные (ARCHITECTURE §2.5).

## 4. Evals и гейт выпуска (D12)

### 4.1 `backend/evals/` [v1.0]
- **Golden dataset**: синтетические снимки **без ПД** + ожидаемые выводы: правило, `action_level`, действие, `risk_level`, exposure.
- Наборы кейсов: проблемные (вывод ожидается), **«чистые»** (выводов быть не должно), пересекающиеся (для `exposure_total`, ECONOMICS.md §3), неполные данные (`data_partial`), неподдерживаемые стратегии (`capability_unsupported`).
- Для AI: набор контекстов (§2.1) + заготовленные ответы модели (корректные, с лишним числом, с числом из нецитируемого факта, причинные без причинного факта, с ID Яндекса) → ожидаемый вердикт валидатора.
- Прогон — pytest-набор; результат привязан к commit SHA (артефакт CI).

### 4.2 Гейт
Новая версия правила / `safety_policy` / `risk_policy` / `exposure_total` / методики замера включается в реестр активных **только если golden-прогон проходит**:

| Критерий | Порог |
|---|---|
| регрессии по ожидаемым выводам | 0 |
| повышение уровня действия относительно ожидаемого | 0 |
| выводы на «чистых» кейсах (ложноположительные) | 0 |
| итог exposure | ≤ суммы карточек и ≥ максимальной карточки |
| AI: пропущенные валидатором необоснованные утверждения | 0 |
| AI: доля fallback на шаблон | метрика (не порог), фиксируется в артефакте |

Намеренное изменение ожидаемого вывода — правка golden dataset в том же PR с объяснением; без неё прогон красный.

### 4.3 [v1.1]
Хранение eval-прогонов в БД, shadow-режим (новая версия считает параллельно, не показывается) и canary-раскатка правил.

## 5. Наблюдаемость (D18)

Метрики v1.0 (знаменатель — за период и по срезам: правило, версия, кабинет):

| Метрика | Числитель / знаменатель | Что показывает |
|---|---|---|
| `sync_success_rate` | успешные синхронизации / все | здоровье Data |
| `provider_error_rate` | ответы Яндекса с ошибкой / все запросы | состояние API Директа/Метрики |
| `stale_data_rate` | workspace с устаревшими данными / активные | свежесть |
| `recommendation_rate` | новые рекомендации / аудиты | плотность выводов по правилу |
| `acceptance_rate` / `rejection_rate` | одобрено или выполнено / отклонено — к решённым, по правилам | доверие к правилу |
| `execution_failure_rate` | `execution_failed` / попытки | надёжность исполнения |
| `state_changed_rate` | `state_changed` / попытки | как часто состояние меняется между одобрением и записью |
| `rollback_blocked_rate` | `rollback_status = blocked` / запросы отката | конфликты отката |
| `verification_not_confirmed_rate` | `not_confirmed` / ручные выполнения со сверкой | заявленное ≠ сделанное |
| `measurement_completion_rate` | замеры с результатом / созданные | полнота замера |
| `llm_fallback_rate` | ответы на шаблоне / запросы к LLM | качество AI |
| `llm_unsupported_claim_rate` | отброшенные утверждения / все утверждения | склонность модели к необоснованному |

Точные определения числителей — при реализации, в коде метрик; таблица выше — смысл.

**«Как часто AdPilot ошибается»** — отдельный показатель для владельца продукта, по правилу: отклонения + `verification_not_confirmed` + откаты. Высокое значение у правила — повод пересмотреть его версию (через гейт §4.2).

## 6. Открытые вопросы

1. **Нормализация и округление чисел** в валидаторе: «≈ 18 400 ₽» против факта `18 437.52` — допустимо ли и по какому правилу.
2. **`summary`**: требовать собственные `evidence_ids` или выводить его из утверждений.
3. **Формат ответа API** «Спросить AI»: сейчас `{answer, citations}` (API_CONTRACT §9) — привести к `{summary, claims[{text, evidence_ids}]}` с обратной подстановкой ссылок (зона API_CONTRACT).
4. **Слова-маркеры причинности** — закрытый список в коде; как ловить причинность без маркеров.
5. **Хранилище метрик D18** (Cloud Monitoring, PostgreSQL-представления) и порог «AdPilot ошибается» — не решены.
6. **Отключение логирования запросов у YandexGPT** — параметр **проверить** (ARCHITECTURE §2.5).
