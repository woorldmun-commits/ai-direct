# Стратегия AdPilot

> Решение владельца продукта **2026-10-03** (заменяет сужение v1.0 от 2026-10-02). **Верх иерархии решений по объёму и правилам:** изменение объёма версий или списка правил аудита начинается с правки этого файла, затем — [VERSION_SCOPE.md](VERSION_SCOPE.md) и [PRD.md](PRD.md). Решения P0 (D2–D18) действуют, кроме изменённых здесь: AI-аналитик (D11) — в v1.0, сегмент — §3.

## 1. Тезис

AdPilot — **независимая AI-система управления рекламой, которая говорит только проверяемую правду.**

Клиент подключает Яндекс Директ и Яндекс Метрику → AdPilot получает реальные данные → проверяет, можно ли им доверять → детерминированный движок находит проблемы и точки роста → AI-аналитик объясняет их и отвечает на вопросы → человек решает → AdPilot измеряет эффект и запоминает результат.

AdPilot должен быть не самым уверенным AI, а **самым проверяемым и честным AI для управления рекламой**.

**Почему независимость — довод, а не слово.** Рекламная площадка зарабатывает на расходе рекламодателя и сама меняет кабинеты: автоприменение рекомендаций Директа включено по умолчанию в новых кампаниях ЕПК, Мастера кампаний и товарных кампаниях и правит фразы, ставки, цели и бюджет; откат — вручную ([справка Директа](https://yandex.com/support/direct/ru/campaigns/auto-recommendations)). ИИ-помощник Директа отвечает по статистике и запускает кампании диалогом в «Простом старте» ([ppc.world, 14.07.2026](https://ppc.world/news/v-direkte-teper-mozhno-zapuskat-reklamu-cherez-dialog-s-ii-pomoschnikom/)). AdPilot стоит над площадкой: проверяет, доказывает и измеряет — в том числе то, что площадка поменяла сама.

Слоган бренда: **«Факты. Решения. Эффект.»**

## 2. TRUTH FIRST — фундаментальный принцип

AdPilot никогда не придумывает, не заполняет и не скрывает отсутствие данных ради красивого ответа. Клиент видит только то, что подтверждается доступными источниками и расчётами. Принцип обязателен для архитектуры, backend, frontend, AI, рекомендаций, аналитики и документации; функция, которая его нарушает, не выпускается.

**Порядок обработки:**
```
External Sources → Ingestion → Validation → Truth Layer → Deterministic Calculations
→ Analysis Engine → Recommendations → AI Explanation → UI
```

**Правила:**
1. Каждое значение имеет `source`, `period`, `fetched_at`, `calculation_type`, `data_status`, `data_sufficiency` (контракт `Value`, API_CONTRACT §2).
2. Никогда не приравниваются: unknown → 0, unavailable → 0, partial → complete, estimated → factual.
3. `"--"` из внешнего API никогда не превращается в 0 автоматически: ноль — только доказанный ноль, иначе «неизвестно».
4. Данных недостаточно для вывода → «Недостаточно данных»; рекомендация, которой нужно это значение, не выдаётся.
5. Данные устарели → показываем время последнего подтверждённого обновления; старые данные не выдаются за свежие, зависящие от них рекомендации ограничиваются.
6. Источники расходятся → расхождение показывается; источник истины для рекомендаций назван явно (PRD §2), молча не выбирается.
7. Денежные значения имеют статус: **FACTUAL** (из источника) · **CALCULATED** (детерминированная формула над фактами, например CPA) · **ESTIMATED** (оценка, всегда с «≈» и формулой) · **UNAVAILABLE** (числа нет, есть причина). Сейчас в `Value` три типа (`actual` · `estimated` · `unavailable`); `calculated` добавляется в контракт v1.0 (VERSION_SCOPE §3.1).
8. AI не источник истины: он получает структурированный `AnalysisContext` только после Truth Layer.
9. AI не придумывает показатели, причины и результаты, не выдаёт оценку за факт и не считает деньги произвольно.
10. Доказательств недостаточно → AI отвечает «Недостаточно данных» или «Не могу определить по доступным данным».
11. Каждая рекомендация содержит: проблему, фактические данные, источник, период, правило/основание, ограничения, предлагаемое действие.
12. У любого вывода есть «Почему AdPilot так считает?» с доказательствами.

**UX-принцип:** Факт → Расчёт → Вывод → Рекомендация. Никогда: AI → утверждение → поиск оправдания.

## 3. Пользователи

Одна платформа, три режима UX; архитектура multi-workspace / multi-account с первого дня (уже в коде).

| # | Кто | Боль | Что получает |
|---|---|---|---|
| 1 | **Собственник бизнеса** | «Я не разбираюсь в Директе. Покажите, куда уходят деньги» | экран «Анализ» простым языком, AI-аналитик, контроль подрядчика |
| 2 | **Маркетолог / директолог** | «Освободите меня от ручной рутины» | находки с доказательствами, рекомендации, история решений, эффект |
| 3 | **Агентство** | «Портфель клиентов и автоматизация» | все кабинеты в одном обзоре, роли, отчёт клиенту |

Лендинг и первый onboarding не строятся исключительно под агентства. Привлечение — через понятную боль: «Показываем, где рекламный бюджет расходуется неэффективно» (слова «потери», «теряет» в рекламе не используем — ст. 5 38-ФЗ, ECONOMICS.md §1).

## 4. Целевой продукт (north star)

```
Данные → Проверка качества → Анализ → Рекомендация → AI объясняет → Preview → Одобрение
→ Apply → Журнал → Измерение эффекта → Память
```

Четыре слоя: **Data Engine** (Директ, Метрика; позже CRM, VK, маркетплейсы) · **Intelligence** (Rules First + AI Second: движок решает, есть ли проблема и хватает ли данных; AI объясняет) · **Action** (preview, одобрение, apply, rollback, kill switch) · **Memory** (решения, гипотезы, исходы, бизнес-контекст).

**Три режима исполнения:** только анализ → с подтверждением («Применить» после одобрения) → автопилот по разрешённым действиям с дневными лимитами, максимальным изменением, журналом, откатом, kill switch и запретом опасных операций.

**Глубина, а не ширина:** AdPilot глубок в Advertising Intelligence + Decision + Action + Effect. Не делаем: коллтрекинг, конструктор сайтов, SEO, CRM, генерацию видео, email-маркетинг, телефонию.

## 5. v1.0 — что входит

Канон перечня — [VERSION_SCOPE.md](VERSION_SCOPE.md). Кратко:
- регистрация и вход; подключение Яндекс Директа (N кабинетов) и Метрики через OAuth; реальные данные, синхронизация по расписанию;
- **Data Health** — постоянный статус-бар: подключения, последняя синхронизация, актуальность, полнота; при устаревших или неполных данных — предупреждение и ограничение рекомендаций;
- Truth Layer и детерминированный Analysis Engine; **ровно три правила** — нулевые конверсии, высокий CPA, площадки РСЯ без конверсий (новое правило — только через этот файл);
- **AI-аналитик (read-only)** — §6;
- рекомендации с доказательствами и «Почему AdPilot так считает?»; решение человека; изменение вносит человек в Директе, AdPilot сверяет по данным и измеряет эффект;
- личный кабинет: **Анализ · Рекомендации · Эффект · Подключения · Настройки** (PRD §5);
- история решений; уведомления; бесплатный первый аудит и подписка;
- RLS и изоляция (D13), юридическая доказательность (D16), DR (D17), evals (D12), наблюдаемость (D18).

**Архитектурное требование v1.0:** рекомендация, исходное состояние объекта, журнал и замер устроены так, чтобы контур v1.1 «Preview → Одобрить → API Apply → Journal → Измерение» подключился без переделки ядра (EXECUTION_SAFETY.md).

**Не входит в v1.0:** запись в рекламные кабинеты через API («Применить»), откат через API, автопилот; CRM, VK Реклама, маркетплейсы.

## 6. AI-аналитик в v1.0 — read-only

Rules Engine — источник истины для расчётов. AI получает структурированный `AnalysisContext` (результат Truth Layer и Analysis Engine текущего workspace) и объясняет его.

| Может | Не может |
|---|---|
| отвечать на вопросы по рекламному аккаунту: что произошло, почему, что изменилось, что рекомендует AdPilot, где расход с признаками неэффективности | изменять рекламу, вызывать Apply (инструментов записи у модели нет) |
| объяснять найденные проблемы и рекомендации | считать финансовые показатели вне структурированного результата |
| показывать конкретные кампании, площадки, метрики | придумывать отсутствующие данные |
| указывать источник, период и статус данных | обращаться к другому workspace |

**Обязательный валидатор** (AI_GOVERNANCE §2–3): фактическое утверждение подтверждается `AnalysisContext`; число существует в контексте или выводится только из разрешённых структурированных данных; при нехватке данных — «Недостаточно данных»; оценка не выдаётся за факт. Ответ, не прошедший проверку, не показывается — вместо него шаблон или отказ.

**v1.1:** AI участвует в действии — Preview → Approval → Apply через Direct API → Journal → Effect Measurement.

## 7. Развитие

| Версия | Что |

AI участвует в действии. Квалификация лидов и офлайн-конверсии (CSV). Кандидат в правило: «изменения, которые внёс не человек» (автоприменение Директа) |

## 8. Вход

Решение владельца: **вход и регистрация по номеру телефона + SMS-код** (D2). Юридический HOLD сохраняется: по ч. 10 ст. 8 149-ФЗ авторизация по абонентскому номеру — в порядке, установленном Правительством; с 07.07.2026 нарушение порядка авторизации наказывается по ст. 13.55 КоАП (по вторичным источникам — до 700 тыс. ₽ для юрлица; сверить по первоисточнику). Поэтому: SMS-вход разрабатываем и **включаем флагом после письменного заключения юриста**; вход через Яндекс ID (прямо разрешён законом, уже в коде) — резерв, чтобы HOLD не блокировал запуск. Детали — LEGAL.md.

## 9. Пилот: метрики и критерий успеха

| Метрика | Что показывает |
|---|---|
| Time to first finding | время от подключения до первой находки |
| Recommendation acceptance rate | доля рекомендаций, принятых к выполнению |
| Rejection reasons | причины «Не буду»: неверные данные · нерелевантное правило · недостаточно контекста · слишком рискованно · долго/неудобно выполнять вручную · другое |
| False-positive rate | доля находок, признанных ложными; выше 15% — стоп продаж, сначала правила |
| AI-аналитик | доля ответов, прошедших валидатор; доля ответов «Недостаточно данных»; жалобы на неверный ответ |
| Free-to-paid conversion | переход с бесплатного аудита на подписку |
| Подтверждённый результат | есть ли хотя бы один измеренный результат после изменения |

Причина «долго/неудобно выполнять вручную» — данные для решения о сроках v1.1.

Оценка для одного разработчика по текущему состоянию кода (нет HTTP-входа, фронт на демо-данных, у воркера нет точки запуска, нет деплоя):

| Нед. | Что |
|---|---|
| 0 (не код) | заявка на API Директа (чтение), OAuth-приложения, уведомление РКН, юрист: оферта, согласие на ПД, вход по SMS; домен |
| 1 | P0: права БД и RLS на users/sessions/memberships, workspace context токенов, `"--"` ≠ 0, CPA на днях досчёта, деление на ноль в замере, видимые сбои синхронизации |
| 2 | Вход (SMS за флагом + Яндекс ID), OAuth Директа и Метрики, выбор кабинетов и целей |
| 3 | Воркер по расписанию, Data Health, ограничение рекомендаций при устаревших данных, маршруты решений |
| 4–5 | Кабинет на реальном API: Анализ, Рекомендации, Эффект, Подключения, Настройки |
| 6–7 | AI-аналитик: `AnalysisContext`, валидатор, YandexGPT, evals |
| 8 | Деплой (Yandex Cloud), бэкапы, мониторинг, error tracking |
| 9 | Первый клиент под присмотром; затем пилот |
